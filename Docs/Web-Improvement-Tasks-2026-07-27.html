Web Apps — Improvement Tasks

Tasks for the next round of work on wergonic-web-apps (client-panel + wergonic-admin). Each task has a short title and description ready to paste straight into the tasks hub. The description states the problem and what needs to be true when it is done — it deliberately does not name files or prescribe a solution. The developer investigates and decides how to fix it.

Each task is then followed by a shaded background note for Amine only. That note carries the diagnosis, the file, and the plain-language explanation. It is not intended for the dev — and if a diagnosis in it turns out to be wrong, the task above it is still correct.

Supersedes the 10 July 2026 edition, which was audited at a8a3416f. Tasks marked New did not exist in that edition; Revised means the problem changed shape and the description has been rewritten.
What changed since 10 July

V2 shipped to production. Not one task on this list was closed.

In 17 days the team merged 30 pull requests and 138 commits across 343 files. The headline change is that on 24 July every v2 feature flag was switched from “dev only” to a hardcoded true, so the new Workers, Team, Measurements, Assessments, Work Library, Settings, Sidebar, Home and Login pages are now live for every customer.

Of the 25 tasks in the previous edition, zero were closed. One was substantially advanced (A4, translations) and three changed shape because of the v2 rollout rather than because anyone worked on them. The remaining 21 are untouched — no commit in the 138 went near them.

Read this first

C1 is still the root cause, and it is now more expensive.

CI still runs typecheck, lint, build and tests in one job, and still builds and pushes the Docker image from a second job that does not wait for the first. Nothing stops broken code from being deployed. This was the number-one item on 10 July and it was not touched.

The cost has gone up, not down. Lint has drifted from 415 problems to 430, and from 37 hard errors to 52, in seventeen days — while v2 was being switched on for customers. Every other task below can silently regress the week after it is closed until this is fixed.

Group A · Live defects in the v2 pages

These were “ship-blockers before the flags go on”. The flags went on. Every one of them is now in front of customers.

A1 Fix Workers page “Measured this month” always showing 0 Bug

On the Workers page, the “Measured this month” card always shows 0, and the change indicator always reads “+0% vs last month” — regardless of how many measurements the organisation actually has. The card never reflects real data. Find out why and make it show the true count and the real month-over-month change.

Background — for Amine

Unchanged since 10 July, but the severity is not. This page is now live, so every customer sees “Measured this month: 0” on their Workers page today.

The API sends back a box with a smaller box inside it. The numbers are in the inner box. The code opens the outer box, looks for the numbers there, finds nothing, and shows 0. The Home page reads the same API correctly, so the two pages disagree with each other. TypeScript would have caught it, but the developer wrote as any — “stop checking this line” — and silenced the linter on the same line.

A2 Add an error state to TableV2 Bug

When a v2 list page fails to load its data, it shows the same “nothing here” panel as an organisation that genuinely has no records — only the wording differs. There is no way to retry. Give the shared table a proper error state with a retry action, and use it on all four v2 list pages.

Background — for Amine

Since 10 July the four pages have been patched to at least pass different text into the empty panel when a load fails. That is a workaround, not a fix: the customer still sees an empty-state graphic where an error belongs, and there is still no retry button. The shared table itself has only two states, loading and empty.

This is the one place where the v2 rewrite repeated a v1 weakness instead of fixing it. Worth fixing in the shared table once, so all four pages get it for free.

A3 Implement New / Earlier grouping in the notifications dropdown Bug

In the notifications dropdown, every notification appears under a heading that says “Earlier” — including ones that arrived seconds ago. There is no “New” section at all. Separately, the unread counter on the bell and the “Mark all as read” action only cover the notifications currently loaded, so older unread ones are never counted and never get marked as read. Build the two groups and make the counter and the action cover everything.

Background — for Amine

A commit in July changed the bell badge colour to red and left a comment referring to “the New/Earlier grouping” — but the grouping itself was never built. A notification that arrived one second ago is still filed under “Earlier”.

The second half is the more serious one. The little red number on the bell only counts the notifications on the first page. If a user has more unread than fit on one page, the rest are never counted and “Mark all as read” silently skips them.

A4 Translate the remaining v2 surfaces i18n Revised

Most of the v2 pages were translated in July, but three surfaces were missed and are still English-only in every language: the Settings page (Organisation tab and Help & Support tab), the passwordless sign-in page that opens from the email link, and the confirmation message shown after submitting a support ticket. Move their text into the translation system and supply all five languages.

Background — for Amine

Good news first. Pull request #910, merged 26 July, did the bulk of this properly — Workers, Team, Measurements, Assessments, Work Library, the sidebar and the login pages, 60 files and about 5,000 new entries across the five languages. That was a real piece of work and it closed most of this task.

What it missed: the Settings page has roughly 30 hardcoded English strings across the Organisation and Help & Support tabs — “Organisation name”, “Country”, “Industry”, “AI & Privacy”, “Create a support ticket”, “App version”, and so on. The passwordless page shows “Signing you in…” and “Verifying your link” in English only. A German customer now gets a fully German app that switches to English the moment they open Settings.

A5 Fix the AI engine setting that cannot be switched on Bug New

In Settings → Organisation, an organisation admin cannot turn AI on. The AI engine dropdown is greyed out until AI consent is already enabled, and the consent switch sits below it — so there is no order of clicks that gets the feature turned on. Make it possible to configure and enable AI from the interface.

Background — for Amine

A circular lock. The dropdown that picks the AI engine refuses to open until AI is switched on; the natural reading of the form is that you pick the engine first. An admin who wants to enable AI clicks Edit, tries the dropdown, finds it dead, and has no way forward from the UI.

Commercially this is the one to care about in this group: it blocks a customer from switching on a feature we sell. Right now the only way to enable AI for an organisation is for us to change it in the database by hand.

A6 Fix the auth page footer links Bug New

On the invitation page and the passwordless sign-in page, the footer offers three links — Privacy, Terms and Data protection — and all three open the privacy policy. Point each one at the right page, or remove the ones we do not have a page for.

Background — for Amine

Both pages were added in July. Three links, one destination, copy-pasted. It is small, but these are the first two screens a brand-new user ever sees, and one of them is where they accept an invitation into the product.

Worth checking with the business side whether we actually have a Terms page and a separate Data protection page to link to — if not, the right fix is to remove the links rather than invent destinations.

Group B · Shared infrastructure

These files are shared by the old and the new app. None of them were touched since 10 July.

B1 Show the backend’s real error message in PageErrorBoundary Bug

When a page fails to load, the user is shown an internal developer message instead of the real reason from the server — for example, the screen literally reads “React query error thrown manually from RULADetailPage”. The actual reason is available but never displayed. This was already fixed on the session detail page (WH-533); around 21 other pages still need it. Look for a fix that covers them all at once rather than page by page.

Background — for Amine

Still 21 pages, still one line in one shared file. Nothing in the 138 commits went near it. When a page fails the customer sees, word for word: “React query error thrown manually from RULADetailPage.” The real reason — “no active organisation”, a permissions error, a validation message — is captured and thrown away.

We already paid to fix exactly this once, on one page. Still the best value on the whole list.

B2 Fix the infinite loop in GlobalAppProvider’s ErrorFallback Bug

When the app catches an unexpected error, instead of redirecting cleanly to the error page it gets stuck repeating the error over and over, which can freeze the browser tab. Reported in the April backlog as item #68, still open, and present in both apps.

Background — for Amine

An error happens, the code immediately resets, which causes the error again, which resets again. It spins forever and can lock up the browser tab. Same code in client-panel and in admin.

B3 Guard useAuth against a failing retrieveCurrentUser Bug

If the backend fails at the moment a user logs in, the app stays on the loading spinner indefinitely. No error is shown and there is no way forward — the user has to reload the page. Handle the failure and show the user something.

Background — for Amine

If the backend has any hiccup during login, the loading spinner spins forever. The user is not shown an error and cannot get past it — their only option is to reload the page. This is on the path every single user takes, every day.

B4 Centralise the MUI onBlur guard across all Formik wrappers Bug Revised

Some forms crash when a field becomes disabled while the cursor is still inside it — which is exactly what happens when a form disables its inputs on submit. To reproduce: open an assessment result, click into the comment box, and press Submit while still focused. This was fixed once for one type of input field (WH-482); we have eight and the other seven are still affected. Find a single fix that covers all of them.

Background — for Amine

Re-counted on the current code: eight input wrappers, one guarded, seven exposed — text fields, text areas, dropdowns, radios and checkboxes. Unchanged since 10 July.

Same class as B1 — a fix was made in one place and never generalised. That pattern is the real finding, not the individual bugs.

B5 Gate ReactQueryDevtools to development builds Cleanup

The React Query developer debugging panel is included in production builds and ships to customers, in both apps. It should only be present when running locally in development.

Background — for Amine

A developer debugging panel is being shipped to customers, and its code is included in the download everyone pays for on first load. It is also declared as a normal dependency rather than a development-only one, which is why nobody noticed.

B6 Make the error boundary’s “Try again” button actually retry Bug

On the error screen, clicking “Try again” appears to do nothing — the same error comes straight back. Nothing is actually re-fetched. Make the button genuinely retry the request that failed.

Background — for Amine

The button says “Try again” but nothing is retried — the same bad data is still cached, so the same error appears instantly. To the user the button looks broken. Cheap to fix alongside B1 and B2, which live in the same two files.

Group C · Build, CI and deployment configuration

The reason defects reach production and stay there. C1 first — nothing else in this document is safe until it is done.

C1 Make the Docker build and push depend on the build job CI

Our pipeline builds and pushes Docker images even when typecheck, lint, build or tests have failed — the deploy half never waits for the check half, and several steps are configured to carry on after an error. Nothing currently stops broken code from being deployed. Make deployment depend on the checks passing.

Background — for Amine

Our pipeline has two halves running side by side. One half checks the code. The other half builds the image and pushes it to the registry. The second half never looks at the result of the first. Tests can fail, the build can fail, and the image ships anyway. Verified again today: still exactly one workflow file, still no dependency between the two jobs.

This was the top item on 10 July, it was not done, and in the seventeen days since we shipped the entire v2 UI to customers with no working safety net. Fund this before anything else on the list.

C2 Clear the lint errors and make lint fail the build CI Revised

Linting reports 430 problems, 52 of them hard errors, and CI is explicitly configured to carry on when the lint step fails — so nobody sees them. Nearly half the errors come from wergonic-admin using a package it never declared as a dependency; it only works today because another app in the repo happens to install it. Clear the errors, declare the missing dependency, then make lint block the build.

Background — for Amine

Re-measured today: client-panel 369 problems (29 errors), admin 30 problems (23 errors), shared library 31 warnings. It has got worse, not better — from 415 problems and 37 errors on 10 July to 430 and 52 now. That is the direct, measurable cost of C1.

Worth knowing: the lint command itself already fails correctly when run by hand. The only thing keeping the pipeline green is one line in the CI file telling it to ignore the result. The admin dependency issue is the other half: admin uses a table library it never asked for, and it works purely by accident because a different app in the same repo installed it.

C3 Add unit tests for the RULA and RAMP score calculations Tests Revised

The repo still has no real automated tests. A test runner is configured in both apps, and the only two test files render a button and assert that true is true. Begin real coverage with the RULA and RAMP risk-score calculations, which decide the risk level we report to the customer and are the most important logic we have.

Background — for Amine

Unchanged: two placeholder files, zero real tests, seventeen days and 138 commits later. If we only ever test one thing, it should be the number that tells a customer whether their worker is at risk of injury.

One correction to the previous edition: it said the scoring code had 24 places asserting a value “definitely exists” without checking. Re-measured on the current code, that is now effectively one. The risk is real but it is the absence of tests, not that specific count — please do not quote the 24 figure to the dev.

C4 Stop Docker image builds from failing silently CI New

Both Docker image builds in the pipeline are configured to carry on after a failure, and the job still reports success. If a Dockerfile breaks, CI stays green and nobody is told; for the admin app the image push is simply skipped, so a deploy quietly does nothing. Make a failed image build fail the pipeline.

Background — for Amine

This is C1’s smaller sibling and found in the same file. There is a legitimate reason one of the two images is built but not pushed — a registry limit on our Digital Ocean plan — but that does not justify hiding the failure. Today a broken build and a successful build look identical on the pull request.

Cheap to do at the same time as C1, and it closes the last way a broken deploy can pass unnoticed.

C5 Wire the API address through the Docker builds CI New

The two apps read the backend address from build-time configuration, but neither is wired up correctly: client-panel’s Docker build never receives the two settings its code depends on, and the admin app declares them but is never passed them by our compose file. Any image built through the normal path therefore has no valid API address. Make both apps receive the API address through the documented build path, and fail the build loudly if it is missing.

Background — for Amine

When the app is built, the backend address is stamped permanently into the JavaScript. If it is not supplied at that moment, the address becomes the literal text “undefined” and every request fails. Client-panel’s Docker file lists ten settings and is missing exactly the two that matter here; admin lists them correctly but our compose file never passes them in.

Production works today, which means something outside these files is injecting the address — undocumented, and nobody currently knows what. That is worth pinning down: it is the difference between “we deploy” and “we can deploy again if the machine dies.” Pair this with F1; a dev fixing F1 alone will find admin still broken.

C6 Make the admin Docker build respect the lockfile Cleanup New

The admin app’s Docker build explicitly disables lockfile enforcement and rewrites dependency checksums on every run, so it can install different library versions than the ones we committed. Client-panel does not do this. Make both apps install exactly what the lockfile specifies.

Background — for Amine

The lockfile is the record of exactly which version of every library we tested against. Admin’s build is told to ignore it, so two builds of the same commit can produce different software. It is almost certainly there because somebody hit an install error once and added flags until it went away.

Low priority on its own, but it means “it worked yesterday” is not evidence of anything for the admin app. Fix it while you are in the file for C5.

Group D · Performance

Measured from the current code. Where a number could not be re-measured without a full production build, it is marked as carried over from 10 July.

D1 Stop packages/ui being bundled whole into the entry chunk Perf

Every user downloads roughly 1.45 MB (compressed) before the login screen even appears. A large part of that is code from our shared component library that the app never uses. Work out why the shared library cannot be trimmed down per app, and cut the initial download.

Background — for Amine

Our shared component library is packaged in a way that tells the bundler “anything in here might be needed”, so it ships all of it, everywhere. It has no build step and no declaration that its files are safe to discard, and the vendor-splitting added on 10 July only applies to third-party libraries, not to our own shared package.

The 1.45 MB figure is carried over from 10 July — re-measuring it needs a full production build. The cause is confirmed unchanged. This and D2 are the same problem and can be one ticket.

D2 Lazy-load the three eager routes in AppRoutes.tsx Perf

Three pages — the invitation page and the two privacy policy pages — are loaded up front on every visit, while every other page in the app is loaded only when opened. Make them load on demand like the rest. Closely related to D1; the two can be done together.

Background — for Amine

Every other page in the app is loaded on demand. These three are loaded up front, and because they reach into the shared component library, they are what drags all of D1’s dead weight into the initial download. Small fix, and it is the trigger for the big one.

D3 Generate PDFs on click, not on page load Perf Revised

Six pages still build the entire downloadable PDF in the background as soon as they open, even though most users never click Download: the four multi-assessment comparison pages, the multi-session comparison page, and the session detail export. The single-assessment result pages already do this correctly. Make the remaining six build the PDF only when the user asks for it.

Background — for Amine

Half of this closed itself. The v2 assessment result pages build their PDF on click, and the old pages that did it on load are no longer reachable now that v2 is on. So the single-assessment case is genuinely fixed.

But the comparison pages were never behind a flag and were missed. Opening a comparison of several sessions — one of the heavier things a user can do — still silently renders a full PDF nobody asked for. Smaller task than it was, same fix, and there is now a correct example in the codebase to copy.

D4 Remove the plotly charting library Perf Revised

We ship two charting libraries. The larger one — 1.17 MB compressed — is now unreachable: the only screen that used it is no longer part of the live app. Confirm it has no remaining users and remove it and its wrapper components from the shared library.

Background — for Amine

This got much cheaper. On 10 July the task was “rewrite the bar chart on top of the charting library we already have”. The v2 rollout retired the screen that used it, so the chart, its wrapper and the whole 1.17 MB library are now dead weight. The task is now a deletion, not a migration.

One caveat for the dev: it should be deleted, not just left unimported. It is still declared as a dependency, so it still slows every install and still shows up in security scanning.

D5 Remove the dead font families from both apps Perf Revised

Both apps fetch font families from Google’s servers on every page load that nothing in the live product uses — two in client-panel and two in wergonic-admin. A third is used only by the /prototype route and is loaded for everyone. Remove the unused ones, load the prototype’s font only on the prototype route, and consider hosting the remaining fonts ourselves to remove the external requests entirely.

Background — for Amine

Re-checked properly, and the previous edition had this partly wrong. Of the four font requests client-panel makes, two are for the old v1 typefaces that nothing in the live app references any more, and one is for the prototype’s display font. Only the last request — the two typefaces the v2 design actually uses — earns its place. Admin makes three requests and two of them are dead.

So it is more waste than we thought, and safer to remove than we thought: this is now mostly deleting leftovers from the v1 design rather than untangling the prototype. Still small, still real, still measured on every single page load.

D6 Remove the unused xlsx dependency Perf

The xlsx library (7.8 MB) is declared as a dependency in both apps but is imported by neither. It is also downloaded from a direct link rather than the normal package registry, which hides it from our security scanners. Confirm it is genuinely unused and remove it.

Background — for Amine

A large library nobody uses, slowing down every install. Re-checked today: still zero imports anywhere in the repo. Note that in April somebody upgraded it rather than removing it, which is a small sign of how little attention the dependency list gets.

It is fetched from a direct download link instead of the normal package registry, which means our security scanners cannot see it — so if a vulnerability is ever found in it, we would not be told.

D7 Load one language instead of all five Perf New

Every user downloads all five languages before the app starts — roughly 956 KB of translation data, of which they need about a fifth. Load only the active language, and fetch a different one when the user switches. This is the single largest avoidable item in the initial download.

Background — for Amine

A direct and slightly ironic consequence of the July translation work: the more we translate, the more every customer downloads. Adding a sixth language today would add another ~180 KB to every first visit worldwide.

The fix is a standard, well-trodden pattern in the library we already use — fetch the one language file the user needs, cache it, fetch another only if they switch. It is a bigger measured saving than D2, D5 and D6 combined, and it does not touch a single page. Best performance value on the list.

D8 Split the admin bundle the way client-panel already does Perf New

The admin app packages every third-party library into one large file, so nothing is usable until all of it has downloaded, and any dependency update invalidates the whole thing for returning users. Client-panel already splits its heavy libraries into separate files. Apply the same configuration to admin.

Background — for Amine

Client-panel got this treatment in the 10 July performance work; admin was not included. Splitting means the browser downloads several files at once instead of one big one, and — more usefully — that updating one library does not force returning users to re-download everything.

Roughly ten lines copied from the other app. Low risk, and worth doing before we look at admin’s other problems, because it makes the app quick enough to actually work in.

Group E · Dead code, dead UI, and small defects

Both the old and the new password form do this, so switching v2 on did not help. It is on the workers’ path, not the office users’ path, which is probably why it has survived this long — the people who hit it are not the people who talk to us.

E3 Remove the vestigial RULA information dialog Dead UI

The RULA detail page contains a help dialog whose entire content is the placeholder word “test”, and nothing in the page can ever open it. Either remove it, or finish it the way the equivalent dialog on the RAMP page works.

Background — for Amine

Somebody left placeholder debug text — literally the word “test” — in a help popup that can never be opened anyway. Harmless today, but it would show the word “test” to a customer the moment anyone adds the button that opens it.

E4 Disable the assessment Submit button until the form is valid UX

On every RAMP, RULA and REBA form, the Submit and Save-and-Continue buttons always look clickable, even when the form is incomplete. The user clicks and is met with an error message instead. The buttons should be greyed out until the form is valid — the app already knows whether it is.

Background — for Amine

The shared button component is even given the answer — it receives whether the form is valid, uses it for the submit logic, and then hardcodes both buttons to “always enabled” anyway. So the user fills the form, clicks, and gets told off.

One file, shared by all three assessment types. Cheap, and it is on the most-used screen in the product.

E5 Clean up dead UI in wergonic-admin Dead UI

Three pieces of dead interface in the admin app. The bulk archive/unarchive action for organisations has been disabled and its code left behind, commented out. The notifications bell has been removed from the header, and the underlying button would not have worked anyway. The “?” icon in the Industry column looks clickable — cursor, click animation — but only has a hover tooltip. Restore or remove each.

Background — for Amine

Buttons that look pressable and do nothing, plus two blocks of commented-out code left in place instead of deleted. The “?” icon shows the hand cursor and the click ripple animation but only reveals a tooltip on hover — so it reads as broken.

E6 Delete the v1 code and routes that can no longer be reached Cleanup New

Now that the v2 pages are live for everyone, the v1 versions behind the old switches can never be displayed again: the old home page, three login forms, the old sidebar and profile menu, the old settings modal, and the old work-cycles table with its dialogs. Two old pages are also still routed — the old Users page and the old Sessions page — reachable by typing the address even though nothing links to them. Remove the unreachable code and retire those two routes, then remove the switches themselves.

Background — for Amine

Roughly four thousand lines that can never run again. Keeping the old version behind a switch during a rollout was the right call; keeping it after the rollout is just carrying weight, and it makes every future change more confusing because there are two of everything.

The two still-routed old pages matter more than they look — see the box below. Retiring them is what makes three separate old bugs disappear without anyone fixing them. Do this only once we are confident the v2 rollout is not being reverted; the switches are the emergency brake and this task removes it.

E7 Remove the remaining type-checking escapes on API data Cleanup New

Two places switch off type checking on data coming back from the backend — the Workers page statistics and the measurement detail header. Both then read fields from that data with no safety net, so a backend change breaks them at runtime instead of at build time. Type the responses properly and remove the escapes.

Background — for Amine

One of these two is the direct cause of A1 — the “Measured this month: 0” bug got through precisely because type checking was switched off on that line by hand. The other has not caused a visible bug yet.

Worth doing as a pair with A1 so the fix does not just paper over the same hole. It is a small task; the reason to raise it at all is that it is the mechanism behind our most embarrassing live bug.

E8 Give paired exports matching filenames Bug New

When a user exports a session comparison they get two files, a spreadsheet and a PDF, which are supposed to share a name so they are obviously a pair. The timestamp is calculated separately for each, so if the clock ticks over between them the two files get different names. Calculate it once.

Background — for Amine

Rare — it needs the second to change between two lines of code — but when it happens the customer gets two files that look unrelated, and around midnight they get two different dates. Two-line fix.

E9 Remove the unused cache-key file Cleanup New

There is a file defining the standard cache keys for assessments that nothing in the app uses. The rest of the app uses a misspelled version of the same key everywhere. Because the spelling is wrong consistently, nothing is broken today — but the first developer who uses the unused file will silently break assessment refreshing. Delete it, or adopt it everywhere and correct the spelling in one pass.

Background — for Amine

Think of it as a label on a filing cabinet. Every drawer is labelled with the same typo, so everyone still finds the right drawer. Someone left a sheet of correctly-spelled labels on the desk. The day anyone uses one, that drawer stops being found — and the symptom is “assessments don’t refresh”, which is hard to trace back.

Not a bug today. It is a trap, and it costs almost nothing to defuse. I mention it because the failure it would cause looks exactly like the kind of intermittent bug we would spend a day chasing.

Group F · wergonic-admin

Admin is live but rarely used, so this is low priority by your call. Both items below share a root cause worth knowing about.

F1 Fix the hardcoded localhost API URL in wergonic-admin Bug

The deployed admin app tries to reach the backend at the address of the machine it is being viewed on, rather than at our server, so every request fails once it leaves a developer’s laptop. It should read the API address from configuration, the way client-panel already does — the settings already exist in admin, they are simply not used. See also C5, which fixes how that address reaches the build.

Background — for Amine

New information since 10 July, and it changes the story. This was fixed on 11 May. The correct version was written, reviewed and merged. On 1 June another branch was merged on top of it and silently reverted it — that branch had been cut before the fix and nobody noticed the conflict resolution threw it away.

So this is not “nobody got around to it”. We paid for the fix, we had it, and we lost it — with no test, no lint rule and no CI check that would notice. Exactly the failure mode C1 exists to prevent.

F2 Restore the expired-login handling in wergonic-admin Bug New

The admin app does not recover when a user’s login expires mid-session. Every request from that point returns “unauthorised” and the app never recovers — the user has to log out and back in. When done, an expired session must renew itself and the failed request must succeed, and if renewal genuinely fails the user should be signed out cleanly. Client-panel already behaves correctly.

Background — for Amine

Logins expire after about an hour. A well-behaved app notices, quietly gets a fresh one, and retries — the user sees nothing. Admin does not, so after an hour it simply stops working until you log out and in.

Same story as F1: this was also written on 11 May and also lost in the same 1 June merge. One careless merge reverted two separate fixes in one file, and nothing caught it for eight weeks. That single fact is a stronger argument for C1 than anything else in this document. Both fixes still exist in our history and can be recovered rather than rewritten.

Re-verdict on the five bugs excluded in July

“Superseded by v2” — checked again now that v2 is actually live

The previous edition set five v1 bugs aside on the grounds that v2 handled them correctly and they would vanish when the old files were deleted. The old files were not deleted — only hidden — so each was re-checked:

  • Fake subscription number and licence date (“123456”, “05/12/2022”) — genuinely gone. The old settings modal can no longer be opened by anyone. The one item that previously needed a decision has resolved itself.
  • Sessions list loading without an organisation — still reachable. The old Sessions page is no longer linked anywhere, but its address still works if typed.
  • Merging sessions never refreshing the list — still reachable, same page, same reason.
  • Bulk user delete not clearing the ticked rows — still reachable. The old Users page is no longer linked, but its address still works.
  • Mismatched cache keys for task models — dormant. The old work-cycles screen that used them is unreachable, so the mismatch cannot fire today. It stays a trap until the code is deleted.

Recommendation: do not fix the middle three. They are only reachable by typing a URL that nothing links to. Retiring those two old routes as part of E6 removes all three at once, plus the fifth, for less effort than fixing any one of them.

Management signals, not code tasks

The clearest signal in this re-audit

We lost two paid fixes to one merge, and nothing noticed for eight weeks.

F1 and F2 were both written, reviewed and merged on 11 May. Both were silently reverted by a single merge on 1 June from a branch cut before them. Nobody found out until this audit. There was no test to fail, no lint rule to trip, and CI would have deployed it either way.

This is worse than the pattern flagged in July. That one was “a fix gets applied once and never generalised”. This one is “a fix gets applied and then disappears.” Both are the same underlying cause: we have no automated way to notice that something that used to work no longer does. That is C1 and C3.

Seventeen days, 138 commits, zero tasks closed

The team was not idle — they shipped the entire v2 UI to production and did a large translation pass, which is real work. But not one item from a 25-item list written specifically as the next round of work was picked up. That is a prioritisation conversation, not a performance one: either the list was never scheduled, or it was scheduled and displaced by the v2 launch.

Worth deciding explicitly this time. If the answer is “ship v2 first”, that is fine — but v2 has now shipped, and six of the items on this list are defects customers are hitting today.

The same fix keeps being applied once and never generalised

Unchanged from July and still true: WH-533 fixed the error message on one page of 21 (B1). WH-482 fixed the blur crash in one input of eight (B4). The task for the dev is not “fix these three” — it is “find where else this pattern applies before closing the ticket.” That belongs in the review checklist, not in a ticket.

The A2 workaround is the newest example: instead of giving the shared table an error state, four pages were each patched to pass different words into the empty-state panel. Four changes, none of them the fix.

Getting worse, measurably

Our safety nets are still switched off, and the debt is now growing.

Lint went from 415 problems and 37 hard errors on 10 July to 430 and 52 today. Test coverage is unchanged at zero. CI still deploys regardless of results. A1 is still a user-visible bug in new code, hidden by a hand-written instruction to stop type-checking that line.

Those are not separate findings. They are one, and the fix is C1 — after which C2 and C3 are what stop it coming back.
