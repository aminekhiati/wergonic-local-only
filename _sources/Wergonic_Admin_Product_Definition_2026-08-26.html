Wergonic Admin
Product Definition

What the internal admin platform is for, what it must contain, and what belongs on every screen. Written for design, and for anyone who needs to know what we are building. Every feature in here was checked against the running code first — nothing is proposed that the platform cannot actually do.

Version 1 · 26 August 2026
Checked against dev on all four repositories
In one line

One place where the Wergonic team can see everything about a customer and act on it

Not a reporting tool, and not a second copy of the customer product. It is the tool our own team uses to run the platform: approve companies, manage their plan, look after their people and their hardware, publish releases, and fix things when they break.

Why we are starting over

What exists today is five flat tables — Organizations, Users, Devices, Firmware, Translations. There is no home screen, nothing has a page of its own, and almost nothing can be acted on. It has fallen a long way behind what the platform actually does. Six concrete examples:

  • The organization table shows five columns. The server already sends twenty-eight fields for every organization — the plan limits, how much of each limit is used right now, the licence date, the subscription, every feature switch. None of it reaches the screen. The information is already there and is simply not being shown.
  • The status column is broken. It reads a field the server does not send, so every organization in the list is drawn as inactive, whatever it really is.
  • Companies can sign themselves up, and nobody sees it. A sign-up creates a company in a pending state, waiting for a Wergonic admin to approve or reject it. Approve, reject, suspend and reactivate are all built and working on the server. None of them exist in the panel — so a new customer sits in the database, invisible.
  • Support messages go nowhere. Customers can send a bug report or a help request from inside the product. Those messages are stored, and have never been shown to a single person.
  • The bell icon in the header does nothing. It is a button with no behaviour behind it.
  • When a recording breaks, a developer fixes it over SSH by running commands on the production server by hand. There are more than twenty of these scripts. That is not a support process.
The real gap

It is not missing columns. It is missing the ability to act

Everything above has the same shape: the platform can already do the thing, and the panel gives nobody a way to do it. That is what this redesign is about. Adding fields to a table would not have fixed any of the six.

Five principles

  1. Every object gets its own page. An organization, a person, a device is not a row with a popup. It is a page you can open, link to, and send to a colleague.
  2. Built for acting, not for browsing. Every screen should end in a button. A screen that only shows numbers and leads nowhere does not belong here.
  3. One search box. Company name, email address, recording number, device serial, sensor id — one field at the top, and it takes you straight there.
  4. Nothing that belongs to the customer. Results, charts, reports and their own configuration live in the customer product. This tool never duplicates them.
  5. One admin role. Everyone on the Wergonic team with access has the same access. There is no permission matrix to design.

What this tool does not do

Worth stating plainly, because the temptation is to keep adding. These are deliberately out of scope:

  • Recording results, charts, measurement data, assessment results, reports. That is the customer product. We do not rebuild it here.
  • Workers, work library, work cycles, categories and labels. Customers configure their own. We do not manage it for them.
  • Logging in as a customer to see what they see. Decided against.
  • The Django backend page. It stays exactly as it is, as the escape hatch for rare technical fixes. This tool does not have to cover everything.

1 · Home

1.1TodayNew

Right now you log in and land on a table of companies. This replaces that with one screen answering a single question: is anything wrong, and what needs me?

The attention list — the point of the page

Sits at the top and is the loudest thing on the screen. One row per problem, each with a count, one line of plain language, and a link that opens the filtered list behind it.

  • Companies waiting for approval — someone signed up and nobody has answered yet
  • Licences expiring in the next 30 days
  • Companies over a plan limit — more people, recordings or assessments than they are allowed
  • Recordings that broke — never finished, or the calculations never completed
  • Assessments that failed
  • Support messages nobody has answered

Platform numbers — second, and quieter

Active companies, people, recordings this month, assessments this month, each with the change against last month. These are for orientation, not for decisions, and the design should say so — they must not compete with the attention list.

Design note

The all‑clear state is the one that will be seen on most days, and it needs to feel good rather than empty. When there is nothing in the attention list, the page should say so plainly and give the numbers the space instead.

2 · Organizations

The centre of the tool. Most support questions start with "what is going on with this company", and today there is nowhere to go and look.

2.1The listRebuilt

Find any customer fast, and see the state of the whole book of business at a glance.

Columns: logo and name, status, country, industry, subscription, licence expiry, number of people, recordings this month against their limit, and a marker for test companies.

Status is four real states, not a dot: Pending, Active, Suspended, Archived. Each needs its own colour, used the same way everywhere in the tool.

Filters: status, country, industry, licence expiring soon, over a limit, test companies, companies that came in through a referral.

From a row: open the company, or suspend and reactivate without leaving the list.

2.2Sign-ups waiting for approvalNew

Companies apply for an account themselves. Someone at Wergonic has to say yes or no. There is no screen for this today at all, and it is the most valuable missing piece in the whole tool.

A card per application showing everything they told us: company name, admin email, phone, type, industry, how they heard about us, whether they already have the hardware kit, and when they applied.

Two decisions:

  • Approve — creates the company's admin account, emails them their login, and the company goes Active. The screen must say this in words before it happens, because it sends a real email to a real customer.
  • Reject — the application is deleted. Also needs saying out loud, because it cannot be undone.
Design note

This should feel like a small queue you clear, not a table you scan. It sits at the top of the Organizations section and carries a count badge in the navigation whenever anything is waiting.

2.3The company pageNew

Everything about one customer in one place. This page does not exist today in any form.

Header, always visible: logo, name, status, country, licence expiry, and the lifecycle buttons that apply to the state it is in — suspend, reactivate, archive.

Overview

Who they are and how to reach them: admin email, phone, company number, address, type, industry, country, how they found us, whether they have the hardware kit, and which company referred them in, if any.

Plan & usage

The four limits every company has — people, admins, recordings per month, assessments per month — each shown as used against allowed, so you can see at a glance who is near the edge. All four are editable here, along with the subscription name and the licence expiry date. AI usage per month sits here too.

Why this matters

These limits already exist for every company and are already enforced. Nobody at Wergonic can currently see them or change them without a developer. This one tab removes a standing request on the dev team.

People

Everyone in the company: name, role, when they were last seen, and whether they are still active. Invitations that were sent but never accepted appear here too, marked when they have expired. From here you can add someone, change their role, or remove them.

Devices

The hardware assigned to this company — serial, model, who has it, which sensors are on it.

Settings

The switches that are set per company: which AI engine they use, whether they consented to AI analysis, whether recordings auto-archive and after how many days, whether referral links are switched on for them, and whether this is a test company. Several of these can only be changed from the Django backend page today.

Danger zone

Suspend, archive, delete. Visually separated from everything else, each one confirmed by name.

3 · Users

3.1The listRebuilt

Find any person on the platform, from any company.

Columns: name, email, role, the companies they belong to, when they were last seen, whether their email is verified.

Filters: role, company, never signed in, not seen in 30 or 90 days.

3.2The person pageNew

Answer "what can this person reach, and why can't they do X" without asking a developer.

Top: name, email, language, when the account was created, when they were last seen, verified or not.

Memberships: one row per company they belong to, with the role they hold in that company and whether they have been deactivated there.

Invitations: every invitation sent to this address, and whether it was accepted, is still open, or has expired.

Actions: send a password reset, change their role in a company, add them to another company, deactivate them.

The thing today's design misses

A person is not in one company with one role. They can belong to several, with a different role in each — a consultant working for three customers is normal. The current panel shows one role per person, which is simply wrong, and it is behind most of the "why can't they see it" questions. The person page has to make the per‑company roles the main thing on the screen.

4 · Health

4.1Broken recordings and assessmentsNew

The list of things that went wrong, and the buttons that fix them. Today this work is done by a developer running commands on the production server.

Scope, stated firmly

This is a repair queue, not a data screen

No results, no charts, no measurement data, no reports. If it is something a customer would look at, it is not on this screen. The only things here are: what broke, who it belongs to, and what to do about it.

Recordings

Columns: number, company, who recorded it, when, how long it ran, and the problem written in plain language — never finished, stuck processing, calculations never completed, no measurement data, a limb missing.

Filters: problem type, company, date range.

Actions: run the calculations again, mark it finished, archive it, delete it. Available on a single row and in bulk.

Assessments

Same shape: name, company, who created it, which type, when, and whether it failed or has been stuck part-finished. Actions: try again, delete.

The detail view

Small and technical. The facts about the recording, the event log the app sent with it, what is wrong, and the same buttons. One screen, no tabs.

Design note

This should read as a queue that gets emptied, and the empty state — nothing is broken — is the one we want to see. It deserves proper design attention, not a grey placeholder.

5 · Devices & sensors

5.1The hardware registerRebuilt

Which kit exists, which company has it, who is carrying it. Support questions usually start with a serial number or a sensor id.

Device list: serial, model, company, assigned person, the sensors attached to it, when it was added. Searchable by serial and by sensor id.

Device page: edit the details, assign or unassign it to a company or a person, attach and detach sensors.

Sensors: a plain searchable list of sensor ids and which limb each one is set up for.

Deliberately not here

No "which devices are out of date" dashboard. The firmware version on a device record is typed in by hand and is not reported automatically, so any screen built on it would be confidently wrong. Not worth designing until the hardware reports its own version.

6 · Releases

6.1Sensor firmwareKeep

Publish the firmware the sensors download. This works today and only needs tidying.

A list of published versions with release date, description, the mobile app version it requires, file size, and which one is currently live. Upload a new version, and mark a version as the current one.

6.2Mobile app version controlNew

Two numbers that decide whether people can use the app at all: the minimum version allowed, and the latest version available. Anyone below the minimum is forced to update before they can continue.

Today these are changed by hand in the Firebase console by a developer. They belong here, as two clearly labelled fields with the current values shown, and a confirmation that spells out the consequence.

Handle with care

Setting the minimum too high locks every user out of the app

This is the single most dangerous control in the tool. It needs to look serious: current values stated, the change stated back before it is saved, and a plain warning of what happens to everyone below that number.

7 · Translations

7.1Import, export, auto-translateKeep

Works today. Upload the English file, fill the gaps in the other languages automatically, export a language back out. Keep it, present it better.

Split by area of the product — web, customer panel, mobile app — with a completeness bar per language.

7.2Edit the words directlyNew

Right now, changing one German sentence means exporting a file, editing it outside the tool, and importing it back. That is why translations drift.

A table: the key, the English, and every language side by side. Search, filter to what is missing, edit in place, save. That is all it needs to be.

8 · Support

8.1Messages from customersNew

Customers can already send a bug report, a feature request, a suggestion or a help request from inside the product. Every one of those has been stored and never shown to anybody.

List: subject, type, who sent it, their company, when, and status.

Message page: the full text, any attachments, and the context needed to answer it — which company, what role, when they were last seen, what plan they are on. Reply from the page.

Needs adding: a status (New, Open, Closed) and an owner. Neither exists on a message today.

9 · Activity

9.1What the team didNew

This tool hands out buttons that approve companies, change plan limits, suspend accounts, force app updates and delete data. There has to be a record of who pressed them.

A plain read-only list: who, what they did, which company or person it affected, when. Filterable by person, company and date. Also shown as a short recent-activity strip on the company page and the person page, so you can see what was done to that record without leaving it.

Patterns that apply everywhere

Worth designing once and properly, because they repeat on every screen in the tool.

  • Global search. One field at the top of every page. Company name, email, recording number, device serial, sensor id. Results grouped by what they are, and picking one opens that page. This is the single biggest time saver in a tool like this.
  • Tables. Sticky header, sortable, paged, choose your columns, export to CSV. The filters live in the address bar, so a filtered list can be pasted to a colleague.
  • Every state designed. Loading, empty, nothing-matched-your-filter, error. Empty states in this tool are often good news and should read that way.
  • Destructive actions. Anything that deletes, emails a customer, suspends an account or changes an app version gets a confirmation that names the thing and says what will happen. No bare "Are you sure?".
  • Status colours. One set for Pending, Active, Suspended, Archived and Failed, used identically everywhere.
  • Detail page shape. Every detail page looks the same: header with the key facts and the main actions, tabs underneath, activity at the bottom. Learn it once, use it everywhere.
  • Dark mode. Already exists in the current panel. Keep it.
  • Desktop first. This is a working tool used at a desk. It should not break on a tablet, but nothing here needs to be designed for a phone.

Suggested order

First

Organizations and Users

The biggest gain for the least work — there is essentially no backend work in either. It closes the approval gap, puts plan limits in our own hands, and answers most support questions on its own. If only one thing gets built, it is this.

Second

Home, Health, Releases

Home gives the tool a front door. Health takes the repair work off SSH. Releases moves app version control out of the Firebase console.

Third

Support, the translations editor, Activity

Each needs a little backend work first. Activity should be built alongside whichever actions ship, not bolted on afterwards.

What design needs to produce

  • The shell — navigation, header with global search, page frame, in dark and light.
  • The shared table pattern, with all four states.
  • The shared detail-page pattern — header, tabs, activity.
  • Every screen listed in this document.
  • Confirmation dialogs, in a normal and a dangerous variant.
  • Status colours and badges, as a small set anyone can reuse.
