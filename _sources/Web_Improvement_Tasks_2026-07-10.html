Web Apps — Improvement Tasks

Tasks for the next round of work on wergonic-web-apps (client-panel + wergonic-admin). Each task has a short title and description ready to paste straight into the tasks hub. The description states the problem and what needs to be true when it is done — it deliberately does not name files or prescribe a solution. The developer investigates and decides how to fix it.

Each task is then followed by a shaded background note for Amine only. That note carries the diagnosis, the file, and the plain-language explanation. It is not intended for the dev — and if a diagnosis in it turns out to be wrong, the task above it is still correct.

25 tasks · 6 groups · audited against the dev branch at commit a8a3416f · 10 July 2026

Scope and how this was filtered

The v2 redesign is currently being applied to the main app on dev. Old v1 files are intentionally kept until the new version is confirmed. Nothing in this document asks anyone to fix or delete code that is only obsolete because of that migration. Every task below is either in code that survives the migration, in the new v2 code itself, or broken for reasons unrelated to it.

Two facts shape the list. First, all v2 feature flags are set to isDevEnvironment, so production still runs v1 entirely and v2 is visible only on the dev deployment. Second, the v2 code did not inherit the v1 bugs — it clears selection after mutations, uses matching query keys, and guards its org-scoped queries. That was checked specifically, and it is good news.

Read this first

C1 is the root cause. Do it before anything else.

CI runs typecheck, lint, build and tests — and then ignores the result and deploys anyway. This is why 22 of the 24 web tasks written in the April backlog are still open today, and why nobody noticed. Until C1 is fixed, every other task in this document can silently regress the week after it is closed.

Group A · Ship-blockers before the v2 flags go to production

Defects in the new v2 code. These must close before the feature flags are flipped on for customers.

A1 Fix Workers page “Measured this month” always showing 0 Bug

On the new Workers page, the “Measured this month” card always shows 0, and the change indicator always reads “+0% vs last month” — regardless of how many measurements the organisation actually has. The card never reflects real data. Find out why and make it show the true count and the real month-over-month change.

Background — for Amine

The API sends back a box with a smaller box inside it. The numbers are in the inner box. The code opens the outer box, looks for the numbers there, finds nothing, and shows 0. Every customer sees “Measured this month: 0” and “+0% vs last month” on the new Workers page.

The part worth raising in review: TypeScript would normally have caught this immediately. The developer wrote as any, which means “stop checking this line”, and added a comment to silence the linter too. So the safety net was switched off by hand, right on the line that has the bug. This is the same theme as C2 — our linter is set to warn, never to block.

A2 Add an error state to TableV2 Bug

When a v2 list page fails to load its data, it shows the same “nothing here” message as an organisation that genuinely has no records. A user cannot tell a server failure apart from an empty list, and there is no way to retry. Give the new shared table a proper error state with a retry action, and use it on all four v2 list pages.

Background — for Amine

When the server fails to return data, the new table just says “Nothing here.” The customer concludes they have no workers, rather than understanding that the request failed. There is also no way to retry other than reloading the page.

This is the one place where the v2 rewrite repeated a v1 weakness instead of fixing it. Worth fixing in the shared table once, so all four v2 pages get it for free.

A3 Implement New / Earlier grouping in the notifications dropdown Bug

In the notifications dropdown, every notification appears under a heading that says “Earlier” — including ones that arrived seconds ago. There is no “New” section at all. Separately, the unread counter on the bell and the “Mark all as read” action appear to only cover the notifications currently loaded, so older unread ones are never counted and never get marked as read. Build the two groups and make the counter and the action cover everything.

Background — for Amine

The dropdown was redesigned to show two groups, “New” and “Earlier”. Only the word “Earlier” was actually built. So a notification that arrived one second ago is filed under “Earlier”.

The second half is the more serious one. The little red number on the bell only counts the notifications on the first page. If a user has more unread than fit on one page, the rest are never counted and “Mark all as read” silently skips them.

A4 Translate all v2 pages i18n

The new v2 pages — Workers, Team, Measurements, Assessments and Work Library — are English only, along with all of their pop-up and confirmation messages. Switching the app language leaves them unchanged. Move all of their text into the translation system and supply the five languages we support. This must be done before the v2 pages are switched on for customers.

Background — for Amine

When we build a page we are supposed to write t("workers.title") and put the actual words in five language files. The v2 pages typed the English words straight into the code instead. It works fine in English and cannot be translated at all.

Not urgent today because v2 is dev-only. It becomes a hard blocker the day we flip the flags, because our German, Dutch and Swedish customers would see an English app. Schedule it as the last v2 task, not the first.

Group B · Shared infrastructure — survives the migration

These files are not being replaced by v2. Fixing them pays off in both the old and the new app.

B1 Show the backend’s real error message in PageErrorBoundary Bug

When a page fails to load, the user is shown an internal developer message instead of the real reason from the server — for example, the screen literally reads “React query error thrown manually from RULADetailPage”. The actual reason is available but never displayed. This was already fixed on the session detail page (WH-533); around 21 other pages still need it. Look for a fix that covers them all at once rather than page by page.

Background — for Amine

Right now, when a page fails to load, the customer sees this on screen, word for word: “React query error thrown manually from RULADetailPage.” The actual reason from the backend — “no active organization”, a permissions error, a validation message — is captured and then thrown away.

We already paid to fix exactly this once (ticket WH-533) but the fix was applied to a single page. The correct fix is one line in one shared file and it repairs all 21 pages at once. Best value on the whole list.

B2 Fix the infinite loop in GlobalAppProvider’s ErrorFallback Bug

When the app catches an unexpected error, instead of redirecting cleanly to the error page it gets stuck repeating the error over and over, which can freeze the browser tab. Reported in the April backlog as item #68 and still open.

Background — for Amine

An error happens, the code immediately resets, which causes the error again, which resets again. It spins forever and can lock up the browser tab.

B3 Guard useAuth against a failing retrieveCurrentUser Bug

If the backend fails at the moment a user logs in, the app stays on the loading spinner indefinitely. No error is shown and there is no way forward — the user has to reload the page. Handle the failure and show the user something.

Background — for Amine

If the backend has any hiccup during login, the loading spinner spins forever. The user is not shown an error and cannot get past it — their only option is to reload the page.

B4 Centralise the MUI onBlur guard across all Formik wrappers Bug

Some forms crash when a field becomes disabled while the cursor is still inside it. To reproduce: open an assessment result, click into the comment box, and press Submit while still focused. This was fixed once for one type of input field (WH-482), but we have eight and the other seven are still affected. Find a single fix that covers all of them.

Background — for Amine

MUI (our component library) sometimes disables a text field while the cursor is still inside it, and when it does, it notifies Formik without passing the usual information. Formik then crashes. We fixed this once, in one input component. There are eight, and seven are still exposed.

One of those seven is reachable right now: focus the comment box on an assessment, press Submit, and the field is disabled while you are still in it. Same class of bug as B1 — a fix was made in one place and never generalised. That pattern is the real finding, not the individual bugs.

B5 Gate ReactQueryDevtools to development builds Cleanup

The React Query developer debugging panel is included in production builds and ships to customers. It should only be present when running locally in development.

Background — for Amine

A developer debugging panel is being shipped to customers, and its code is included in the download everyone pays for on first load.

B6 Make the error boundary’s “Try again” button actually retry Bug

On the error screen, clicking “Try again” appears to do nothing — the same error comes straight back. Nothing is actually re-fetched. Make the button genuinely retry the request that failed.

Background — for Amine

The button says “Try again” but nothing is retried — the same bad data is still there, so the same error appears instantly. To the user the button looks broken.

Group C · Build and CI

The reason defects reach production and stay there. C1 first.

C1 Make the Docker build and push depend on the build job CI

Our pipeline builds and pushes Docker images even when typecheck, lint, build or tests have failed — the deploy half never waits for the check half, and several steps are configured to carry on after an error. Nothing currently stops broken code from being deployed. Make deployment depend on the checks passing.

Background — for Amine

Our pipeline has two halves running side by side. One half checks the code. The other half builds the image and pushes it to the registry. The second half never looks at the result of the first. Tests can fail, the build can fail, and the image ships anyway.

This is why 22 of the 24 web tasks from the April backlog are still open — nothing ever told anyone. Fix this before funding any other task on this list, otherwise everything we close here can quietly come back.

C2 Clear the lint errors and make lint fail the build CI

Linting currently reports 415 problems across the repo, 37 of them hard errors, and it is configured never to fail the build — so nobody sees them. Most of the errors come from wergonic-admin using a package it never declared as a dependency; it only works today because another app in the repo happens to install it. Clear the errors, declare the missing dependency, then make lint block the build.

Background — for Amine

The linter has been raising its hand for months and it is configured so that nobody has to look. Combined with C1, that means no automated check can currently stop bad code.

The admin dependency issue is the interesting one: admin uses a library it never asked for. It works today by accident, because a different app in the same repo installed it. Any change to how we install packages breaks admin with no warning.

C3 Add unit tests for the RULA and RAMP score calculations Tests

The repo has no real automated tests — the only two test files are empty placeholders. Begin coverage with the RULA and RAMP risk-score calculations, which decide the risk level we report to the customer and are the most important logic we have.

Background — for Amine

We have no real tests at all. If we only ever test one thing, it should be the number that tells a customer whether their worker is at risk of injury. That calculation currently has 24 places where the code asserts “this value definitely exists” without checking — each one is a potential crash or a wrong score.

Group D · Performance

Every number below was measured from a real production build, not estimated.

D1 Stop packages/ui being bundled whole into the entry chunk Perf

Every user downloads roughly 1.45 MB (compressed) before the login screen even appears. A large part of that is code from our shared component library that the app never uses — the admin app, for instance, ships a full carousel and date picker despite using neither. Work out why the shared library cannot be trimmed down per app, and cut the initial download.

Background — for Amine

Our shared component library is packaged in a way that tells the bundler “anything in here might be needed”, so it ships all of it, everywhere. The proof: the admin app’s bundle contains 187 references to the date picker and 51 to the carousel — and admin uses a date picker in exactly one file and a carousel nowhere at all.

Every customer downloads roughly 1.4 MB before they can even see the login form. This and D2 are the same problem and should be one ticket if the dev prefers.

D2 Lazy-load the three eager routes in AppRoutes.tsx Perf

Three pages — the invitation page and the two privacy policy pages — are loaded up front on every visit, while every other page in the app is loaded only when opened. Make them load on demand like the rest. Closely related to D1; the two can be done together.

Background — for Amine

Every other page in the app is loaded on demand. These three are loaded up front, and because they reach into the shared component library, they are what drags all of D1’s dead weight into the initial download. Small fix, and it is the trigger for the big one.

D3 Generate PDFs on click, not on page load Perf

Opening any assessment result page (RAMP, REBA, RULA, MEC) silently builds the entire downloadable PDF in the background, even though most users never click Download. It should only be built when the user asks for it.

Background — for Amine

Every time anyone opens an assessment result, the browser quietly builds the entire downloadable PDF in the background — even though most people never click Download. It burns CPU and memory on every page view for nothing.

D4 Replace react-plotly.js with @nivo/bar Perf

We ship two separate charting libraries. One of them weighs 1.17 MB compressed and is used for a single bar chart; the other is already installed and already draws our pie and line charts. Consolidate onto one and remove the unused library.

Background — for Amine

We are carrying two separate charting libraries. One of them is enormous and is used for exactly one bar chart. The other one is already installed, already used elsewhere, and can draw that bar chart.

D5 Move prototype-only fonts out of index.html Perf

Every page load fetches four font families from Google’s servers. Three of them are used only by the /prototype route, so live customers are paying for fonts they never see. Load the prototype’s fonts only where they are needed, and consider hosting the remaining fonts ourselves to remove the external requests. This does not require touching any prototype code.

Background — for Amine

This one is related to the prototype, but it is not a “delete it later” item — it costs us today. Production customers are downloading three font families that only the /prototype route uses, on every single page load, from Google’s servers.

Worth doing now rather than waiting for the cleanup, because it is a genuine load-time cost on the live app and the fix does not touch any prototype code.

D6 Remove the unused xlsx dependency Perf

The xlsx library (7.8 MB) is declared as a dependency in both apps but appears to be used by neither. It is also downloaded from a direct link rather than the normal package registry, which hides it from our security scanners. Confirm it is genuinely unused and remove it.

Background — for Amine

A large library nobody uses, slowing down every install. It is also fetched from a direct download link instead of the normal package registry, which means our security scanners cannot see it — so if a vulnerability is ever found in it, we would not be told.

E4 Disable the assessment Submit button until the form is valid UX

The “?” icon in the Industry column looks clickable — cursor, click animation — but does nothing. Restore or remove each. Not related to the v2 migration; admin is not part of it.

Background — for Amine

Buttons that look pressable and do nothing. The “?” icon in the Industry column shows the hand cursor and the click ripple animation, but only has a hover tooltip — so it reads as broken. These are not migration leftovers; admin is not part of the v2 redesign.

Group F · wergonic-admin

Admin is live but rarely used, so this is low priority by your call. F1 is included anyway because it is cheap and may explain most of admin’s problems.

F1 Fix the hardcoded localhost API URL in wergonic-admin Bug

The deployed admin app tries to reach the backend at the address of the machine it is being viewed on, rather than at our server, so every request fails once it leaves a developer’s laptop. It should read the API address from configuration, the way client-panel already does — the settings already exist in admin, they are simply not used.

Background — for Amine

The deployed admin app tries to reach the backend at the user’s own computer, not at our server. On a developer’s laptop that happens to work, which is why it was never noticed. Anywhere else, every request fails.

Introduced on 27 January by assia-mad. You mentioned admin “has a lot of problems” — it is quite likely this is most of them. The fix is about five lines, and the correct version already exists in the other app. Worth doing even at low priority, if only to find out what admin’s real problems are once it can talk to the API.

Deliberately excluded

Superseded by v2 — do not spend time on these

All of the following are real bugs in v1 code, and all of them are already handled correctly in the v2 replacement. They will disappear when the old files are deleted:

  • FinishedSessionsTable missing its enabled: !!organizationId guard — MeasurementsPage v2 handles it.
  • Merge sessions never invalidating the list — MeasurementsPage v2 clears and refetches.
  • DeleteMultipleUsersButton not clearing the selection after delete — TeamPage v2 clears it.
  • Task-model query key mismatch (task_models vs task-models) — WorkCyclesV2 does not use those mutations.
  • Hardcoded subscription data ("123456", "05/12/2022") in the old settings modal — the new OrganizationTab reads the real organisation fields.
One decision needed

Those five are still live in production today

Because every v2 flag is set to isDevEnvironment, production customers are still running v1 and are still hitting all five of the bugs above. If the v2 rollout is more than a month or two away, a few of them are worth patching in v1 anyway — the fake subscription number and license date especially, since every organisation admin currently sees “Current subscription: 123456” and “License expiration: 05/12/2022”.

If the rollout is imminent, ignore them entirely.

Two management signals, not code tasks

The same fix keeps being applied once and never generalised. WH-533 fixed the error message on one page of 21 (B1). WH-482 fixed the blur crash in one input of eight (B4). WH-482’s retry fix went to client-panel and never to admin. The task for the dev is not “fix these three” — it is “find where else this pattern applies before closing the ticket.” That belongs in the review checklist, not in a ticket.

Our safety nets are switched off. A1 is a user-visible bug in brand-new code, hidden by an as any and an eslint-disable, in a repo where the linter only warns (C2) and CI ignores the result anyway (C1). Those are not three findings. They are one.
