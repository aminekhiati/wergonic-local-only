Platform Overview

What is Wergonic

Wergonic is an ergonomic risk assessment platform that combines smart workwear sensors (Movesense 9-axis IMU via Bluetooth Low Energy), a Flutter mobile app for field recording, a React web dashboard for analysis, and a Django backend for data processing and AI-powered reporting. The platform enables ergonomists and occupational health professionals to objectively measure and assess workplace ergonomic risks using standardized methods (RAMP, RULA, REBA, MEC) with real-time sensor data, rather than relying solely on manual observation.

User Roles

Role Description Access
WERGONIC_ADMIN (Superadmin) Platform-level administrator Admin Panel + Client Panel + full backend access
ORG_ADMIN Organization administrator Client Panel — manage users, sessions, assessments for their org
ERGONOMIST Ergonomic assessor / consultant Client Panel — record sessions, create assessments, generate reports
WORKER Field worker being assessed Mobile App only — cannot access web Client Panel

The 3 Interfaces

  1. Admin Panel (wergonic-admin) — Superadmin-only. Manages organizations, users across orgs, devices, firmware.
  2. Client Panel (client-panel / cloud.wergonic.com) — Main user-facing web app for ORG_ADMIN and ERGONOMIST roles. Sessions, assessments, reports, work cycles, user management.
  3. Mobile App (wergonic-flutter / ergotech) — Flutter app for field workers and ergonomists. Sensor pairing, calibration, session recording, offline data collection, sync.

Authentication & User Management

Login Methods

Email Magic Link (Passwordless)

  • User enters email on login page
  • Backend sends a sign-in link via email (Firebase Auth)
  • User clicks link → redirected to /auth/process-login?link=<encoded>
  • Frontend completes Firebase sign-in, receives ID token
  • Token used for all subsequent API calls
  • Mobile app has its own magic link endpoint (/users/auth/mobile-passwordless-signin/)

Email + Password

  • Standard email/password login via Firebase Auth
  • Available on both web and mobile

Worker Account Creation

  • Public endpoint at /users/create-worker-account/
  • Web form at /auth/signup (AccountCreationPage)
  • Creates a WORKER role user

Worker Blocking on Web: If a WORKER logs into the Client Panel, they are immediately signed out with error message "Workers cannot access this application." Workers can only use the mobile app.

Password Reset Flow

  1. User visits /auth/password-reset → enters email
  2. Backend sends reset email via Firebase
  3. User clicks link → /auth/password-reset/new
  4. User enters new password → backend updates Firebase + Django password
  5. Confirmation email sent

Session/Token Management

  • Firebase Authentication manages tokens
  • ID tokens automatically refreshed by Firebase SDK
  • Axios interceptor attaches Authorization: Bearer {idToken} to every API request
  • Backend verifies Firebase token on each request, updates last_seen timestamp
  • Custom claims on Firebase token include: {role, organization_id}

Organization Management

Multi-Organization Support

  • Users can belong to multiple organizations via UserOrganization join table
  • Each membership has its own role (a user can be ERGONOMIST in one org, ORG_ADMIN in another)
  • One organization is "active" at a time — user can switch active org
  • Switching active org: POST /users/organizations/{orgId}/change-to-active/

Organization Registration

  • Public endpoint at /organizations/register/
  • Creates organization + admin user in one step

Organization Fields

  • Name (unique), Country, Address, Industry (A-U industry codes)
  • Contact phone, Company registration number
  • Logo (URL, uploaded to Firebase Storage)
  • Subscription info: current_subscription, license_expiration
  • Limits: max_number_workers (default 500), max_number_admins (default 5), max_number_sessions_month (default 3000), max_number_assessments_month (default 3000)
  • AI engine selection: Gemini (default) or Chat-button-001
  • Hardware kit access: OWN, BORROWED, NO_ACCESS

Invitation System

  • Admin sends invitation to email with role assignment
  • Invitation has 7-day expiration
  • Accept: POST /organizations/invitation/{invitationId}/
  • Creates UserOrganization record + Profile if needed
  • Sends welcome email

Mobile App — Complete Feature Map

3.1 Onboarding & Setup

First Launch Experience

  1. Splash Screen (/) — App initialization, Firebase auth check
  2. If not logged in → Login Page (/login)
    • OAuth provider buttons
    • "Login with Email" option → /login_with_email
  3. Post-login → Welcome Screen (/welcome)
    • Checks for firmware updates
    • Organization selection if user belongs to multiple orgs

Sensor Pairing Process

  1. Navigate to Pairing Screen (/work_session_config/pairing)
  2. App scans for Movesense sensors via MDS SDK
  3. Discovered sensors listed with name/ID
  4. User selects sensor → assigns to a limb (rightArm, leftArm, trunk, head, hand, forearm, chestStrap)
  5. MDS establishes BLE connection → receives serial number confirmation
  6. Sensor stored in local database with limb assignment
  7. Multiple sensors can be paired — one per limb, up to 7 total

Calibration Process

Full Calibration (/sensor-calibration — LimbsCalibrationPage):

For each connected limb (2-4 steps depending on limb type):

Step 1 — Pre-Establish Streams:

  • Opens IMU data streams for all devices
  • Reduces latency during actual calibration

Step 2 — Device Validation:

  • Verifies all expected devices are connected and receiving data

Step 3 — Natural Position Capture:

  • User holds limb in neutral/relaxed posture
  • System captures ~2 seconds of IMU data
  • Computes quaternion orientation reference

Step 4 — Bent Position Capture (trunk/head only):

  • User bends to maximum comfortable range
  • System captures ~2 seconds
  • Creates second reference point for range-of-motion

Calibration storage: CalibrationDataEntity saved per limb with quaternion + posture state + timestamp.

Per-Limb Recalibration (/recalibration — LimbsRecalibrationPage):

  • Allows recalibrating a single limb without redoing all

Organization Selection

  • Switch Organization (/settings/switch_oranization)
  • Lists all organizations user belongs to
  • Switching changes active org context for all operations

3.2 Session Recording

Work Session Configuration (/work_session_config)

  • Select session type: Work Task or Work Cycle
  • Select worker profile (who is being assessed)
  • Select workplace/tag
  • Select which limbs to record (via SelectableLimbsCubit)
  • Connect sensors → go to pairing if needed
  • Calibrate → go to calibration if needed

Work Task Sessions

Full flow:

  1. Configure session (worker, limbs, workplace)
  2. Connect & calibrate sensors
  3. Start recording → Work Session Recording Screen (/work_session)
  4. Live metrics displayed during recording (see below)
  5. User can add work tasks/breaks via Work Tasks Screen (/work_session/WorkTasks)
  6. Pause/resume as needed
  7. End session → data saved locally → sync to cloud

Work Cycle Sessions

  • Pre-defined cycle from Factory → Line → Workstation → Task hierarchy
  • Select cycle via Work Cycle Screen (/work_session_config/work-cycle-screen)
  • Select specific tasks via Work Cycle Tasks List (/work_session_config/work-cycle-task-screen)
  • Auto-advance between tasks (if timeBasedWorkCycles enabled, advances every newWorkCycleFrequency minutes, default 180)
  • Same recording UI as Work Task, but with structured task progression

Data Collected During Recording

  • Per limb (BLE sensors): Accelerometer (3-axis), Gyroscope (3-axis), computed Quaternion, Elevation Angle, Angular Velocity, Pitch, Roll, Yaw, Temperature
  • Heart rate (chestStrap): BPM, confidence, RR intervals
  • Location (if enabled): GPS latitude, longitude, altitude, accuracy, speed
  • Activity recognition: Walking, running, driving, still, biking (via phone sensors)
  • Session events: Task start/end, break start/end (user-marked)

Live Metrics During Recording

The recording screen shows real-time:

  • Elevation Angle — current angle + yellow/red threshold indicators
  • Angular Velocity — current speed + accumulated over intervals
  • Trunk Bending — forward and side angles
  • Heart Rate — BPM (if chestStrap connected)
  • Vibration Detection — confidence percentage for hand tremor/shaking
  • Activity Mode — walking/driving/still/running/biking icon
  • Session Timer — elapsed recording time
  • Sensor Status — connection state per limb (connected/disconnected/reconnecting)
  • Battery Level — per sensor (checked every batteryCheckIntervalSeconds, default 10s)

Voice/Audio Feedback

  • Configurable voice guidance intervals (10-60 seconds)
  • Announces posture warnings when thresholds exceeded
  • Controlled by isAudioFeedbackEnabled and voiceFeedbackIntervals settings
  • Limb feedback priority configurable via limbsFeedbackOrder

Pause/Resume Behavior

Pause:

  • Timer stops
  • BLE subscriptions suspended
  • CSV writes stop queuing
  • UI shows pause state with resume button

Resume:

  • Timer resumes from paused time
  • Re-establishes BLE subscriptions
  • CSV writes resume
  • Time gap handled (no data loss, just a jump)

Session Events (Tasks & Breaks)

  • During recording, user can mark task start/end and break start/end
  • Each event creates a SessionEventEntity with:
    • Event type: taskEvent or breakEvent
    • Event name (user-entered or from work label)
    • Phase: start or finish
    • Timestamp
  • Events are synced to backend and used for per-task analysis

Background Execution

  • Android foreground service keeps recording when app is backgrounded
  • Notification shows "Recording in progress"
  • Battery optimization exemption requested (disable_battery_optimization)
  • BLE connections maintained via MDS SDK
  • Screen lock: Recording continues (foreground service)
  • Device reboot: Session data saved to local DB, but active recording is lost. Session remains in local storage for later sync.

Session End

  1. All CSV writers flushed (force write buffered data)
  2. File handles closed
  3. Session directory compressed into ZIP
  4. Local database updated: syncStatus → createdNotSynced
  5. Session saved to local DB with all metadata
  6. Session Summary Page (/session_summary) shown with:
    • Duration
    • Connected devices summary
    • Sync status
    • Option to view report or sync immediately

3.3 Lite Mode

What is Lite Mode

Phone-based recording using the device's built-in accelerometer and gyroscope instead of external Movesense BLE sensors.

How It Differs from Full Mode

Aspect Full Mode (BLE) Lite Mode (Phone)
Sensors External Movesense Phone accelerometer/gyroscope
Limbs Up to 7 simultaneously 1 only (phone placement)
Accuracy High (calibrated IMU) Lower (consumer phone sensors)
Heart Rate Via chestStrap Manual entry only
Calibration Multi-step per limb Single 5-second phone calibration
Cost Requires sensor hardware No additional hardware

Lite Mode Calibration (/liteMode)

  1. User places phone on chest/torso
  2. Stand still in natural position for ~5 seconds
  3. System captures reference quaternion from phone sensors
  4. Single-point calibration stored

Limitations

  • Only 1 limb tracked at a time
  • No multi-sensor reference data (hand/forearm)
  • Lower accuracy from consumer-grade phone sensors
  • No heart rate without manual input
  • Sampling rate depends on phone hardware (typically 50-100 Hz vs consistent 104 Hz from Movesense)

3.4 Sensor Management

Sensor Discovery & Pairing

  • BLE scan using MDS SDK (MdsAsync.startScan())
  • Scans for Movesense sensors by advertised name
  • DFU mode: Separate scan using flutter_blue_plus filtering for "dfu" names
  • Discovered sensors show: name, ID, signal strength

Connection Per Sensor

  1. Stop scanning
  2. Mds.connect(id) → MDS SDK handles connection
  3. Callback receives serial number on success
  4. BLE connection parameters set: min interval 48.75ms, max 100ms
  5. Device stored in local DB with limb assignment

Multi-Sensor Support

  • Supported limbs: rightArm, leftArm, trunk, head, hand, forearm, chestStrap (7 total)
  • Typical usage: 3-5 sensors (both arms + trunk, optionally head + hand/forearm)
  • Limit: One sensor per limb, up to 7 simultaneous connections
  • Managed via SensorConnectionCubit tracking Map<Limbs, BleDeviceEntity>

Sensor Status Indicators

  • Connected — green, actively receiving data
  • Disconnected — red, no data
  • Reconnecting — yellow/orange, attempting reconnection
  • Scanning — blue, discovery in progress

Battery Information

  • Checked periodically during sessions (default every 10 seconds)
  • Tracked per device via SensorBatteryCubit
  • Displayed as percentage

Firmware Information

  • Device firmware version retrieved via MDS /Info path
  • Available firmware listed from backend (/devices/firmwares/)
  • Firmware Update Screen (/firmware) — DFU via Nordic DFU library
  • firmware_update_available_dialog.dart — prompts user when update available

flag: Firmware update dialog flow appears incomplete (TODO in code)

Disconnect Behavior

  • MDS callback fires on disconnect
  • SensorConnectionCubit updates state to disconnected
  • During recording: automatic reconnection attempted

Reconnection Behavior

  • reconnectMissingDevices() called periodically during recording
  • Up to 3 retries per device, 10-second intervals
  • Clears Android GATT cache before retry
  • Re-initiates full Mds.connect() flow
  • Manual reconnection available from settings

3.5 Offline Mode

What Works Offline

  • Full session recording (BLE + lite mode)
  • Sensor pairing and calibration
  • Session history viewing (locally stored sessions)
  • Past reports (if previously cached)
  • All settings changes
  • Work label/task creation for session events

What Doesn't Work Offline

  • Session sync/upload to cloud
  • Work cycle download/refresh
  • Work category refresh
  • New user login (requires Firebase auth)
  • AI report generation
  • Firmware download

Sync When Back Online

  • InternetCubit monitors connectivity state
  • Sessions marked notSynced or createdNotSynced in queue
  • User can manually trigger sync from session history
  • No automatic retry with delay — relies on user action or background check on reconnect

Visual Indicators

  • Online/offline state shown in UI
  • Sessions show sync status badge:
    • notSynced — local only, not yet uploaded
    • createdNotSynced — remote session created, files not uploaded
    • historyNotSynced — old session needing resync
    • fullySynced — fully synced to cloud

flag: No automatic retry mechanism for failed syncs. User must manually trigger.

3.7 Settings & Configuration

All Mobile App Settings

Measurement Settings:

  • feedbackType — Immediate vs Accumulated feedback
  • voiceFeedbackIntervals — 10-60 seconds between voice alerts
  • feedbackRefreshRate — 50-200 ms (controls UI feedback latency)
  • standardImuRate — 52, 104, or 200 Hz (BLE sample rate)
  • refImuRate — 52, 104, or 200 Hz (reference limb rate)

Sensor Settings:

  • gyroRange — Gyroscope full-scale: ±250, ±500, ±1000, ±2000 °/s
  • accRange — Accelerometer full-scale: ±2, ±4, ±8, ±16 G
  • integralGainValue — Mahony filter integral gain (default 0.0)
  • proportionalGainValue — Mahony filter proportional gain (default ~2.0)
  • headSensorPosition — chestOriented vs trunkOriented

Session Settings:

  • workSessionType — WorkTask vs WorkCycle
  • timeBasedWorkCycles — Auto-advance cycles by time
  • newWorkCycleFrequency — Minutes between auto-advance (default 180)
  • sessionDurationLimit — Max session hours (default 8)
  • tnoArchiveGeneration — Auto-compute TNO after session

Calibration:

  • isTwoPointCalibrationEnabled — Toggle 2-point vs 1-point calibration

Vibration Detection:

  • isVibrationDetectionEnabled — Detect hand tremor/shaking
  • useImprovedVibrationDetection — Physics-based vs simple variance
  • confidenceThresholdHigh / confidenceThresholdLow — Detection sensitivity

System:

  • liteMode — Enable phone sensor mode
  • isHrActive — Enable heart rate tracking
  • offlineMode — Disable cloud sync
  • autoStartSession — Auto-begin recording on app launch
  • enableLocation — Track GPS during session
  • appLanguage — EN, NL, SV, DE, ES
  • batteryCheckIntervalSeconds — 5-60 seconds (default 10)
  • limbsFeedbackOrder — Priority list for feedback

Developer Mode Features

  • Performance overlay (FPS, memory, frame time)
  • CSV performance benchmarking
  • Sensor data logs (raw IMU output)
  • Shake gesture → Report Bug Sheet
  • useNewCsvSystem — Toggle between legacy and new CSV writer
  • showExtraTiles — Show advanced measurement tiles
  • isPerformanceOverlayEnabled — FPS counter

Report Problem (/reportProblem)

  • Bug/issue reporting form
  • Creates ticket via /tickets/ endpoint
  • Attachments supported

4.3 Assessments (/dashboard/assessments)

Assessment Types

RAMP (Rapid Assessment of Musculoskeletal Posture)

  • Source: Manual (user fills forms) or Generated (from sensor data + AI)
  • 7-step form process:
    1. Postures — 8 posture questions with body diagrams
    2. Movements and Repetition — Repetitive movement assessment
    3. Lifting Work — Lifting assessment (weights, frequency, posture)
    4. Pushing and Pulling — Push/pull force assessment
    5. Influencing Factors — Environmental factors (vibration, cold, stress)
    6. Strenuous Work — Strenuous activity assessment
    7. Perceived Physical Discomfort — Body map for discomfort marking
  • Results page: Risk score with color coding, detailed breakdown, comments
  • AI Continuation: GeneratedRAMPResultsPage at /continue sub-route uses Gemini AI to auto-fill/suggest assessment values based on session sensor data
  • Routes:
    • List: /dashboard/ramp-assessments
    • Detail: /dashboard/ramp-assessments/:id (redirects to postures step)
    • Results: /dashboard/ramp-assessments/:id/results
    • Multi-compare: /dashboard/ramp-assessments/results

RULA (Rapid Upper Limb Assessment)

  • 3-section form:
    1. Left Side — Left arm/hand/wrist analysis
    2. Right Side — Right arm/hand/wrist analysis
    3. Neck, Trunk and Legs — Head, trunk, leg assessment
  • Each section computes individual scores → combined final score
  • Routes:
    • List: /dashboard/rula-assessments
    • Detail: /dashboard/rula-assessments/:id (redirects to right side)
    • Results: /dashboard/rula-assessments/:id/results
    • Multi-compare: /dashboard/rula-assessments/results

REBA (Rapid Entire Body Assessment)

  • Similar structure to RULA but assesses whole body
  • Routes:
    • List: /dashboard/reba-assessments
    • Detail: /dashboard/reba-assessments/:id
    • Results: /dashboard/reba-assessments/:id/results
    • Multi-compare: /dashboard/reba-assessments/results

MEC (Metabolic Energy Cost)

  • Generated from session sensor data via POST /sessions/{sessionId}/assesments/mappings/
  • Calculates metabolic cost based on:
    • Arm postures (dominant arm + forearm analysis)
    • Wrist position using geometric calculations
    • 6 work posture models for different arm elevation ranges
    • Frequency analysis of arm movements
  • MEC-specific threshold configuration
  • Routes:
    • Results: /dashboard/mec-assessments/:id/results
    • Multi-compare: /dashboard/mec-assessments/results

4.4 Reports & AI Generation

Gemini AI Analysis

  • Trigger: POST /sessions/{sessionId}/generate-gemini-analysis/
  • Input: Session data + language + optional work label tags
  • What the AI receives (prompt):
    • Worker profile (age, weight, dominant arm)
    • Measurement duration with extrapolation caveat
    • Posture & movement data with risk zone thresholds
    • Arm elevation analysis (50th/90th percentile limits)
    • Trunk bending analysis (20-45° and >45° thresholds)
    • Wrist angular velocity data
    • HR/HRV stress indicators
  • Risk Zone Thresholds in Prompt:
    • ARM ELEVATION: Green <25%, Yellow 25-50%, Red >50%
    • TRUNK BENDING 20-45°: Green <12.5%, Yellow 12.5-25%, Red >25%
    • TRUNK BENDING >45°: Green <6%, Yellow 6-12.5%, Red >12.5%
  • Output: Actionable ergonomic recommendations in the requested language
  • Languages: Full localized prompts in EN, SV, DE, ES, NL
  • Stored: In Session.ai_report JSONField
