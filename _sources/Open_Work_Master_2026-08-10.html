Read this first

Three things that change how you read the rest.

1 · A developer overruled the CEO in the code and then deleted the evidence. On 3 August Farhad ruled that head backward bending is −5° and that a RAMP score of 1.5 is a bug. On 6 August a backend developer rewrote the tests to state that −10° and 1.5 are intended — describing both as "confirmed by the team" — and on 7 August deleted those tests entirely. The product code was never changed, so it still contradicts the written decision. This needs one ruling from you, not a ticket. See DEC-1 and DEC-2.

2 · The backend team did real work; the web team did not touch its list. Since 5 August the backend shipped a full automated test suite from nothing and closed fourteen audit findings. In the same period the web apps closed four items out of thirty-seven, and the two most expensive ones — the pipeline that deploys broken code, and the admin app that points at localhost — are untouched for the third list in a row.

3 · Backend fixes are on dev, not in production yet. dev is twenty commits ahead of main on the backend. Every backend item marked closed below is closed on dev. The web apps and the mobile app have dev and main level, so their fixes are live.

Do first

Live customer harm, a cross-company data hole, or something that blocks everything else. Eight items.

ISO-1Restore company separation on work categories, labels and session eventsBackend

Any logged-in user can read and write another company's session labels, label categories and session events. The checks that keep each company's data private are commented out and replaced with a plain "is logged in" check. Restore them, and scope every query to the organisation making the request rather than to an ID taken from the web address.

Note for you

This has now been reported as the number-one blocker in the 20 July audit and again on 6 August, and it is still byte-for-byte unchanged — six views in one file. The neighbouring bulk-create endpoint still enforces the guard, which is the proof the checks were meant to be there and were switched off deliberately at some point. Worth asking who removed them and why before it is simply put back.

ISO-2Stop session creation trusting worker and ergonomist ID numbersBackend

When a session is created the backend looks up the worker and the ergonomist by their ID numbers and never checks they belong to the company making the request. Anyone with a valid login can attach another customer's worker or ergonomist to their own session just by sending a different number. Restrict the lookups to the request's organisation and return "not found" otherwise.

Note for you

Five unscoped lookups in one function. The request already works out the caller's organisation a few lines above, so the fix is mechanical — but it needs a test, because nothing currently proves it. I have not checked whether this has ever been exploited; I am reporting that the code allows it.

DATA-1Stop every mobile session overwriting the worker's gender and dominant armMobileBackend

The app sends the worker's gender and dominant arm in a format the system does not recognise, and the backend writes whatever it receives straight onto the profile without checking. The stored value ends up outside the list of values the system itself allows. This happens on every session start, for every worker, and nobody is told. Fix the format the app sends, and make the backend reject values that are not one of the allowed options.

Note for you

Unchanged since 6 August. It also re-corrupts workers whose details were entered correctly from the web, and the same code overwrites weight, age and resting heart rate from the session payload — so mobile silently beats anything an admin set in the client panel.

Ask Farhad whether gender or dominant arm feed any ergonomic calculation (DEC-4). If they do, this has been quietly affecting results and we need to know how far back.

DATA-2Workers invited from the Users page never get a worker profileWebBackend

Adding a worker from the Users page creates their login and sends the invitation but never creates their worker profile, and the form does not even ask for a Worker ID — which is now required. When that worker logs into the mobile app and starts a session, the request fails with a server error and no explanation. Either collect the Worker ID there and create the profile alongside the account, or stop offering the worker role on that form and point admins at the Workers page, which does it correctly.

Note for you

Two different ways to add a worker, one of which has never worked. That is the actual problem — decide which one is the real path before anyone writes code (DEC-3).

ERR-1Login hangs forever if the backend failsWeb

If the profile request fails at the moment a user logs in, the app stays on the loading spinner indefinitely. No error is shown and there is no way forward — the user has to reload the page and hope. Handle the failure and show the user something.

Note for you

This is on the path every single user takes, every day, and the admin app already handles it correctly. It has been on the list since 20 July.

UI-1Worker password reset lands on a "page not found"Web

A worker resets their password, types the new one, presses Save — and lands on a 404. The password change itself works; the page they are sent to afterwards does not exist. Send them somewhere real.

Note for you

Confirmed again today: the destination is referenced in two places and registered in none. Both the old and the new password form do this. It is on the workers' path, not the office users' path, which is probably why it has survived this long — the people who hit it are not the people who talk to us.

PIPE-1Make the Docker build and push wait for the checksWeb

Our pipeline builds and pushes Docker images even when typecheck, lint, build or tests have failed — the deploy half never waits for the check half, and several steps are configured to carry on after an error. Nothing currently stops broken code from being deployed. Make deployment depend on the checks passing.

Note for you

This was the top item on 10 July, the top item again on 27 July, and it is still exactly as it was. Every other web item on this list can silently regress the week after it is closed until this is done — and we have direct evidence of that: two paid fixes (PIPE-2 and UI-2) were written and merged on 11 May and silently reverted by one merge on 1 June. Nobody found out for eight weeks.

The backend now has the safety net the web apps do not. Same company, same standard should apply.

PIPE-2Fix the admin app pointing at localhostWeb

The deployed admin app tries to reach the backend at the address of the machine it is being viewed on rather than at our server, so every request fails once it leaves a developer's laptop. It should read the address from configuration the way the client panel already does — the settings exist in the admin app, they are simply not used. One line.

Note for you

We already had this fix. It was written, reviewed and merged on 11 May, and thrown away by a merge on 1 June from a branch cut before it. Pair this with PIPE-5, which fixes how the address reaches the build — a developer fixing this alone will find admin still broken.

High

Customer-visible, wrong data, or high leverage. Forty-two items, grouped by where the work lands.

Backend — company separation and access

ISO-3Scope work-cycle tasks that have no parent modelBackend

The task list is meant to show only your own company's tasks, but it also returns every task that is not linked to a parent model — which happens with legacy or imported data — and those are visible, editable and deletable by every company. Drop that branch or scope it.

ISO-4Block re-pointing a session's activity or condition to another company'sBackend

When an activity is first attached to a session the backend checks it belongs to your company. When that attachment is edited afterwards it forgets to re-check, so a user can point their own session at another company's activity — leaking its name and inflating that company's usage counters. Apply the same check on update.

ISO-5Change the default API permission from "anyone" to "logged in"Backend

The framework default is set to allow anyone, so any endpoint where a developer forgets to declare permissions is publicly accessible. Switch the default and mark the genuinely public endpoints — login, register, password reset — explicitly.

ISO-6Restrict allowed hosts and the API documentation in productionBackend

The backend accepts any host name, and the full Swagger endpoint listing is readable without logging in. Restrict both outside development.

Backend — wrong numbers

DATA-3MEC questions 11 and 12 measure the wrong thingsBackend

Questions 11.1 and 11.2, "head in red zone", currently report the difference between the head and trunk angle — which is what question 12 was defined to measure. Question 11 should use the head's own angle. Question 12 is declared in the response and never calculated, so it comes back empty on every MEC ever produced. Fix both.

Note for you

Net effect today: the head's own angle is never reported anywhere, question 11 is mislabelled, and a worker whose head moves with their body always scores near zero.

DATA-4Pair head and trunk readings by time, not by list positionBackend

The two sensors record at different rates, so from the first dropped sample onwards the calculation compares the head at one moment with the trunk at another. Match them by timestamp.

Note for you

A fix for this was written and then reverted earlier this year. Ask why before it is re-done — there may have been a real reason, and if there was it needs writing down.

DATA-5Task-scoped RAMP mixes in whole-session hand-distance dataBackend

RAMP can be run for a single task inside a session. Five of its six posture measures correctly look only at that task's time window; the sixth — how far the hands are from the body — uses the whole session. So a task-specific report is contaminated by behaviour from the rest of the session.

DATA-6Print trunk and head bending percentiles in the Word reportBackend

The percentiles for trunk and head bending are calculated, stored, and then dropped at the last step: the Session Percentiles table only knows how to print an Elevation Angle row and an Angular Velocity row, and trunk and head have neither. Add forward and backward bending rows for both. Skip side bending.

Note for you

Side bending is excluded on Farhad's instruction — he does not consider it accurate enough to publish.

DATA-13A body part that was not measured must not be reported as "Acceptable"Backend

RAMP item 1.6 shows "Missing: Forearm", a total time of 00:00:00 and no zone — and still prints "Score 0 — Acceptable". The same happens in item 1.5 when only one arm is missing. It should read "Not assessed". A body part we did not record must never show green.

Backend — errors and reliability

ERR-5Separate user mistakes from real crashesBackend

Session creation, session import, firmware create and update, and organisation creation each wrap everything in a single catch-all that returns a generic server error. A duplicate value, a missing field and a genuine crash all come back looking identical, so no client app can show anything useful. Return proper validation errors for things the user can fix; keep server errors for real failures.

Note for you

Session import is the one that matters most — an import failing with no reason is a support call every time. This also hides our real error rate in Sentry, because everything is logged as one generic exception.

Assign this before ERR-2 and ERR-6, or with them. Those two depend on the shape this settles; doing them first means the team will guess at a shape that is about to change.

ERR-10Assessments get stuck at "In progress" foreverBackend

If the background worker dies mid-generation nothing ever touches the row again — no timeout, no retry, no cleanup. The row looks clickable but does nothing, and the only thing the user can do is delete it. Add a timeout and a visible failed state.

PIPE-8A background job runs every minute, in every server process at onceBackend

The session-status check is meant to run roughly every five hours. Two overlapping schedulers mean it is scheduled every single minute, and it also starts up inside every server worker process. The same heavy job fires many times over, hammering Firestore with redundant reads and racing against itself. Use one scheduler and the right cadence.

UI-11Notifications name the assessment number as if it were the measurementBackend

The bell says "RAMP generated from measurement #2224" — 2224 is the assessment number; the measurement is #7010. Assessments with no measurement print the literal text "measurement #None", and several assessments on one measurement all print as identical lines because the text never includes the assessment number.

UI-12Stop guessing which company a web request belongs toBackend

Web and mobile each keep their own selected organisation and a header tells the API which to use. If a user has never touched the web organisation switcher, the web falls back to whatever organisation their phone is on — and when a user belongs to several, that fallback picks one with no ordering at all. Set the web organisation properly on first web login, make the lookup deterministic, and reject a request with no platform header instead of guessing.

Note for you

This was demonstrated in July: the same account and the same address, one request with the header and one without, returned two completely different companies' assessments. No error, no warning. It is the quietest item on this list and the one hardest to explain to a customer if it ever surfaces.

Backend + web together

UI-8A generated RAMP looks finished when it is notBackendWeb

The backend marks an assessment "Completed" the moment the calculation finishes, and the app reads that as "a human has finished it". So a RAMP with six of about forty questions answered shows a green Completed chip, a Download PDF button, and a risk bar reading "0 red / 0 yellow / 5 green". Add a status between "In progress" and "Completed", show "5 of 40 answered" instead of a risk verdict, and do not offer the PDF until it is genuinely complete. There is also no way to reopen a completed assessment — add one.

UI-9Make the Home inbox a queue that can emptyBackendWeb

"To review" is literally every assessment that has finished calculating, so nothing can ever leave it. The distinction we actually need — whether a human has answered it — already exists in the data but is not filterable; exposing it is a one-line backend change. At the same time, the inbox and Recent activity list the same events, and every generated assessment appears twice because two separate events fire seconds apart. Inbox should be things that went wrong or are waiting on you; Recent activity should be things that went fine. Nothing in both.

UI-6Three different worker counts, and admins are counted as workersWebBackend

The Workers page, Home and the licence bar show three different numbers, all labelled "workers". Every user account automatically gets a worker profile and the list never filters those out, so every admin and ergonomist is listed and counted as a worker. On top of that "Active workers" is fed by the search box, so typing changes the count. Agree what a worker is, count it once, and reconcile the three surfaces.

Web — errors the user cannot act on

ERR-2Show the backend's real error message instead of the developer'sWeb

When a page fails to load the user is shown an internal developer message rather than the real reason from the server — one screen literally reads "React query error thrown manually from RULADetailPage". The actual reason is available and thrown away. Around 21 pages are affected. Look for the fix that covers them all at once rather than page by page.

Note for you

We already paid to fix exactly this once, on one page. Still the best value on the whole list. Depends on ERR-5.

ERR-3Make "Try again" actually retryWeb

On the error screen, clicking "Try again" appears to do nothing — the same bad data is still cached so the same error comes straight back. Make the button genuinely re-fetch what failed.

ERR-4Fix the error fallback that loops and can freeze the tabWeb

When the app catches an unexpected error it resets immediately, which causes the error again, which resets again. It spins forever and can lock up the browser tab. Same code in both apps.

ERR-6Stop dropping per-field validation messagesWeb

When the backend rejects a form and says which field was wrong, the app only looks for a single general message and ignores the per-field ones. The user gets a vague toast — sometimes an empty one — and no indication of which field to correct. Handle every shape the backend replies in, through one shared helper, and show the message against the field it belongs to.

ERR-7Home shows a confident dashboard of zeros when the backend is downWeb

Home never checks whether its data loaded. If the backend is unavailable it renders a complete dashboard with every number reading 0 — which looks exactly like a healthy but empty organisation. The previous Home had a loading skeleton and an error message; the new one lost them.

Web — defects

UI-2Restore expired-login handling in the admin appWeb

The admin app does not recover when a login expires mid-session. Every request from that point returns "unauthorised" and the app never recovers — the user has to log out and back in. An expired session must renew itself and the failed request must succeed; if renewal genuinely fails the user should be signed out cleanly. The client panel already behaves correctly.

Note for you

Also written on 11 May and lost in the same 1 June merge as PIPE-2. Both fixes still exist in our history and can be recovered rather than rewritten.

UI-3Guard the remaining form inputs against the blur crashWeb

Some forms crash when a field becomes disabled while the cursor is still inside it — which is exactly what happens when a form disables its inputs on submit. To reproduce: open an assessment result, click into the comment box, press Submit while still focused. This was fixed once for one type of input; seven of our eight are still exposed. Find a single fix that covers all of them.

UI-4Every count on Home stops at 10Web

The app asks the server for 10 items and then counts how many came back, so the number can never go above 10 no matter how big the real backlog is. "Run risk assessment" fetches the newest 10 and shows 0 if those happen to have assessments — even with 200 older ones waiting. The real total is already in the same reply and is ignored.

UI-5Exposure limit colours are assigned by row position, not by valueWeb

On the Head and Trunk cards the safest band is coloured yellow and backward bending is coloured green, because the colour comes from where the row sits rather than from the number. The Head card also shows "—" for every recommended limit while still colouring its bands red and amber — a risk colour with no threshold behind it. And two cards on the same screen are both titled "Arm angular velocity" with different numbers.

Note for you

The head has no limits of its own: the code treats anything that is not an arm as a trunk, so the head's 50th percentile is compared against the trunk's threshold. That is a separate decision — does the head get its own published limits, or do we stop showing colours for it?

UI-7Warn before losing a half-filled assessmentWeb

There is no "you have unsaved changes" warning anywhere in the app, and no autosave. Fill in half a RULA, REBA or RAMP, click away or close the tab, and everything since the last save is gone silently. These are long multi-page forms.

Note for you

Probably the bug our users hit most often, and it has never been built rather than being broken. It was promised as "will be done today" in July and confirmed absent since.

UI-13Finish the translations, Swedish firstWeb

The Settings page (Organisation and Help & Support tabs), the passwordless sign-in page and the confirmation shown after submitting a support ticket are English-only in every language. Move their text into the translation system and supply all five languages. Separately, verify Swedish end to end and make the language choice save.

Note for you

The July translation pass was real work and closed most of this — 60 files, around 5,000 entries. What is left means a German customer gets a fully German app that switches to English the moment they open Settings.

Swedish is the commercial one. In July, switching to Swedish translated exactly one word.

Web — pipeline and performance

PIPE-3Clear the lint errors and make lint block the buildWeb

Linting reports 430 problems, 52 of them hard errors, and CI is explicitly told to carry on when the lint step fails so nobody sees them. Nearly half the errors come from the admin app using a package it never declared as a dependency — it only works today because another app in the repo happens to install it. Clear the errors, declare the missing dependency, then make lint block the build.

PIPE-4Write the first real web tests, starting with the risk scoresWeb

The repo has two test files and both assert that true is true. Begin real coverage with the RULA and RAMP risk-score calculations, which decide the risk level we report to the customer.

Note for you

The backend went from nothing to a full suite in about a week this month. Point the web devs at what they did and at the same target list — it removes the "where do we even start" excuse.

PIPE-5Wire the API address through the Docker buildsWeb

Both apps read the backend address at build time, and neither is wired up correctly: the client panel's Docker build never receives the two settings its code depends on, and the admin app declares them but our compose file never passes them in. Any image built through the normal path has no valid API address. Fail the build loudly if it is missing.

Note for you

Production works today, which means something outside these files is injecting the address — undocumented, and nobody currently knows what. Worth pinning down: it is the difference between "we deploy" and "we can deploy again if the machine dies."

PERF-1Load one language, not all fiveWeb

Every user downloads all five languages before the app starts — roughly 956 KB of translation data, of which they need about a fifth. Load only the active language and fetch another when the user switches.

Note for you

Best performance value on the list — a bigger measured saving than the next three combined, and it does not touch a single page. It is also a direct consequence of the translation work: adding a sixth language today would add another ~180 KB to every first visit worldwide.

PERF-2Stop bundling the whole shared component library into the first downloadWeb

Every user downloads roughly 1.45 MB compressed before the login screen even appears, and a large part of it is code from our shared component library the app never uses. Work out why it cannot be trimmed per app, and cut the initial download. Closely related to PERF-3 — they can be one ticket.

Mobile

DATA-7Hand recordings upload with their columns shifted when vibration detection is offMobile

The uploaded data file always includes the vibration column headers, but the rows only write those values when the setting is on. Everything after that point shifts left, so values line up under the wrong headers and the backend reads corrupt hand data for the whole recording. Write placeholders so headers and rows stay aligned.

DATA-8Location recording stops working after the first sessionMobile

If location tracking is on it works for the first session after the app starts and then never again — the internal stream is closed at the end of that session and never re-opened. Every session after that records no location data, silently. Recreate it per session.

DATA-9Female workers are stored as "other"Mobile

Gender is written in upper case and read back checking for lower case, so the two never match and any female worker is quietly interpreted as "other". No crash — just wrong data feeding the ergonomic reports. Same root cause as DATA-1; do them together.

ERR-8"Finish session" reports success even when saving failedMobile

When a user taps Finish the app asks the recording and the data file to stop, waits ten seconds, and moves on whether or not they succeeded. A failure is logged for us, and the user is taken to the summary as if everything worked — with numbers that may be incomplete. If a step fails or times out, tell the user and offer to retry rather than presenting partial results as final.

Note for you

This is the highest-consequence version of the pattern in this whole document: the user is shown a successful outcome for something that failed. It would also explain sessions with numbers that look wrong for no clear reason — speculation on my part, but cheap to rule out.

ERR-9The scan screen spins forever when Bluetooth is offMobile

If a user opens the sensor-scan screen with Bluetooth turned off, the error never reaches the screen and they are left staring at a spinner with no explanation and no way forward. Show "Bluetooth is off".

WIRE-1Move mobile onto the work-library endpointsMobile

The backend moved activities and labels to a new module and the web app already switched over. Mobile still calls the old addresses for labels, events and categories. It works today only because the old ones have not been shut down; the moment they are, every activities and labels action on mobile fails.

Note for you

Mobile is further along than the July audit said — the session status values and the activity and condition group endpoints are done. What is left is the label and event side. This is now a finishing job, not a migration.

WIRE-2Work-break markers are sent with an ID the backend does not haveMobile

Every break is recorded using a hard-coded label ID of 0, and backend IDs start at 1. The break upload is rejected every time, and it can break the whole session save. Resolve the real ID at runtime, or have the backend provide a canonical one.

WIRE-3Body-part names are sent in a format the backend rejectsMobile

Mobile sends display names — "Right Arm" — where the backend only accepts the compact internal form. None of them match, so the backend concludes the session recorded no body parts and marks them all missing, and the web's limb filter then finds nothing for that session.

WIRE-4A task with no duration crashes the whole task listMobile

The backend allows a work-cycle task with no duration — for example one imported from Excel with the time column left blank. Mobile assumes there is always a number and crashes the entire task list for that work-cycle, so the operator cannot even start recording.

Decisions for you

Seven items that are not developer calls. Nothing below should be written as a ticket until it is answered.

DEC-1 · answer this first

Head backward bending: −5° or −10°?

On 3 August Farhad reviewed the calculation issues and ruled: "It should be 5° backward. Zero is the main criteria but not practical." The mobile app was changed to −5° and that work shipped.

On 6 August a backend developer rewrote the tests to state that −10° is intended, with a comment reading "confirmed by the team… the original audit read this as head-should-be −5, but that was overruled". On 7 August those tests were deleted.

The product code was never changed. So today the risk verdict and the Word report use −10° for the head, RAMP uses −5°, and the phone uses −5°. The three disagree, and what shipped is not what was decided in writing.

What is needed: one ruling from you, then one fix applied everywhere. Trunk backward stays −10° either way — that one is a deliberate modification of the RAMP standard and is not in question. Do not let anyone "harmonise" head and trunk into a single value.

DEC-2

RAMP score 1.5 — bug or intended?

Same story, same week, same developer. Farhad ruled: "It is a bug — should be % of time and will never be 1.5." The tests were then rewritten to say 1.5 is "a valid half-step" and "confirmed by the team", and then deleted. The code still returns 1.5, and two colour functions in the web app still disagree about what colour 1.5 should be.

Handle this in the same conversation as DEC-1. The pattern matters more than either number: a written CEO decision was reversed in the code and the record of it removed.

DEC-3

Which worker-creation path is the real one?

Workers can be added from the Workers page, which collects a Worker ID and creates the profile correctly, or from the Users page, which does not and produces an account that fails on its first session. Two paths, one broken. Your answer decides whether DATA-2 is a fix or a removal.

DEC-4

Do gender and dominant arm feed any ergonomic calculation?

Ask Farhad. Every mobile session has been writing invalid values into both fields (DATA-1). If they feed a calculation, results have been quietly affected and we need to know how far back. If they do not, DATA-1 is still worth fixing but is not urgent for accuracy.

DEC-5

Should two companies be allowed the same name?

Company names are unique across the entire system today, so the second company called "Nordic Logistics" to sign up is refused with "This company name is already taken". This may be deliberate. It is the same shape as the Worker ID rule we just fixed, so it is worth answering deliberately rather than by accident.

DEC-6

Self-signup: build it or delete the page?

There is a "Create an Account" page with an email field and a Submit button that does nothing, and no link anywhere in the product leads to it. Given that passwordless sign-in and referral registration both shipped recently, the real question is whether self-signup is on the roadmap at all.

DEC-7

Head exposure limits — publish them or stop colouring them?

The exposure limits card colours the head's bands red and amber while showing "—" for every recommended limit, because the code treats anything that is not an arm as a trunk. Either the head gets its own published limits, or we stop showing a risk colour for it. This is an ergonomics call, not a UI one. Relates to UI-5.

Parked on purpose

  • Phone vs report warning thresholds for the head — Farhad wants a table of the phone's criteria against the report's criteria built first, then a decision. Different reference standards are in play.
  • Three different colouring rules for one session — the pie charts, the risk gauges and the measurement screen each colour the same arm differently. Farhad wants an example report and a discussion with Liyun and Micke before anything changes.
