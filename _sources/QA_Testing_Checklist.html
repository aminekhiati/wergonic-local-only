1 · How to use this list

Two runs, one list. Nothing here needs code — it's all clicking, tapping and looking carefully.

The daily run — every morning, about 50 minutes

Section 3. It answers one question: is anything obviously broken right now? Log in, open the main screens, record a short session, check the data arrives. It is not meant to find subtle bugs — it's meant to catch a broken build before the whole team wastes a day on it. If everything passes, say so in the team chat in one line and move on to your other work.

You don't need to record 32 passes. Only report what fails.

The release run — before every release

Sections 4 to 7, all of it. Takes one to two days. This is the full sweep: every screen, every field, every error message, plus the cross-cutting pass in section 7. Here you do keep a record of what passed and what failed, so we know the release was actually covered.

What the star means

★ in the full list = this item is also part of the daily run. Same check, listed once, so the two runs can never drift apart.

Every item is written the same way

ID  ·  what you do  —  what should happen.

M-16★Assign a sensor to a limb — it connects, shows its serial number and a battery percentage

If what happens is different from what's written after the dash, that's a bug. Some items are deliberately open ("check what happens when…") — those are where you use your judgement and ask if you're unsure.

When something fails

Write a bug ticket the way the QA Onboarding & Study Guide describes — title, steps, what happened, what you expected, screenshot, environment, severity. Put the check ID in the ticket (for example "fails M-16"), so we can trace it back here.

Before you file anything, read section 8.

Some things in the apps are unfinished on purpose or already reported. Filing them again wastes your time and the developers'.

Keep this list alive.

Every real bug you find that isn't covered by an item here should become a new item. That's how the list grows — it should be noticeably longer in six months than it is today. Tell us when you add one so the IDs stay unique.

Get these set up and written down before your first run. Ask the team for the accounts.

Two things to confirm on day one.

The environment names are being reorganised, so ask which URL is the current test environment before you start. And the admin panel currently points at a backend running on the developer's own machine — it can't be tested on a normal URL yet. Ask before you spend time on section 6.

Accounts you need

One of each role, on the test environment, so you can check that people only see what they should:

  • Org admin — sees everything in one organisation, including Team
  • Ergonomist — records and analyses, but no Team page
  • Worker — mobile app only; must be refused on the web
  • Superadmin — for the admin panel
  • A user who belongs to two organisations, to test switching

Browsers and screens (web)

Chrome is your everyday browser. For the release run, also go through the main flows in Edge, Safari and Firefox. Screen sizes to check: a 1366-wide laptop, a 1920 desktop, and a tablet width. If something only breaks on one of them, say which one in the ticket.

Phones (mobile)

At least one Android and one iPhone, and ideally one older, slower Android — that's where recording problems show up first. Always write the phone model and OS version in the ticket.

The sensor kit

Some checks need the physical sensors and the workwear — they're marked needs the kit in section 4. You can't do them from your desk. If the kit isn't always available to you, do the kit part of the daily run at least twice a week, and always before a release.

8 · Known and already reported — do not file these

Read this before your first run, and check back before filing anything that looks odd in these areas. These are either unfinished on purpose or already known to the team.

Unfinished on purpose — they'll be built later

WhereWhat you'll see
Mobile · vibration panelThe time display and the limb toggle aren't built. The panel looks half-empty. Not a bug.
Mobile · firmware updateThe dialog offers an update, but the button doesn't start it. Known.
Mobile · sensor list buttonsPair, unpair and disconnect in the settings sensor list do nothing when tapped. Known.
Mobile · work cycle auto-advanceThe setting exists but the app doesn't actually move to the next task by itself.
Mobile · failed syncsThere is no automatic retry. If a sync fails, the user has to press sync again. That's the current design, not a bug.
Web · real-time updatesThe web panel doesn't update by itself — you have to refresh to see a new measurement. Expected for now.
Admin panelPoints at a local backend, so it doesn't work on a deployed address. Already on the team's list.

Looks wrong, is intentional

The head and trunk "0° to 10°" posture band.

It actually covers −5° to 10° — it includes a small amount of backward bending. This was decided deliberately, so a value of −3° landing in the "0–10°" band is correct behaviour. Don't report it.

When you're not sure whether something is a bug.

Ask. It's much better to ask a quick question than to either stay silent about a real bug or file a ticket for something that was designed that way. Both cost the team time — asking costs almost nothing.

Keeping this section honest

Anything about recording, sensors or sync is more serious than anything else in this document. If a measurement can't be recorded, or recorded data doesn't arrive in the web panel, that's a critical bug — report it immediately, don't wait until the end of your run.
