Mobile — what is left

Everything still open on the phone, checked in the code today against the latest dev (96aed6a6). Grouped by the kind of problem rather than by screen, because most of these share a cause and are cheaper to do together.

How to read this

What is decided and what is yours

Each task says what happens today and what the product must do instead. Where a behaviour is named — a screen stays open, an error is shown, an order is followed — that is decided and not up for discussion. How to build it is yours.

If an item turns out to need a change we have not described — a new screen, a new setting, a different workflow — stop on that item and tell us. Do not decide it yourself.

Groups 1 and 2 are the ones that matter. Group 6 can wait.

Group 1 · Finish the move to the new Work Library

The biggest single piece of work here, and the one with a deadline attached: the old endpoints still answer, and the day they are switched off the phone stops working. Four items, one job.

M1The phone still calls the old address for labels, categories and eventsHigh

The backend moved activities and conditions to /work-library/… and the web app followed. The phone still calls /categories/… for every category, label and event: fetching a category with its labels, creating a category, creating a label, and uploading the session’s events.

This works today only because the old endpoints have not been switched off. The day they are, every activity and label action on the phone stops, and no session events upload at all.

Do

Move all four calls onto the Work Library API, the same one the web app uses. Statuses and the activity lists are already on the new API, so this is a finishing job rather than a rewrite — follow what is already there.

Do this one first. M2, M3 and M4 all touch the same code, and doing them separately means touching it three more times.

Finished when

Nothing in the app calls /categories/ any more, and a full session — pick an activity, pick a condition, take a break, finish, sync — arrives complete on the web.

Open Work reference: D1

M2Break markers never save, and they take the rest of the session with themHigh

A break is recorded against label number 0. That label does not exist on the backend, so the upload is refused. Because all of a session’s events go up in a single request, one break means none of that session’s events are saved — not the activities, not the tasks, nothing.

Do

A break is a real thing that happened during the recording and it must reach the server. Send it as something the backend accepts rather than as a label that does not exist.

Whatever the shape, one event failing must never stop the others: send them so a single bad event is rejected on its own and the rest still land.

Finished when

A session with two breaks in it shows both breaks and all its activities on the web after sync.

Watch out

Check what actually reaches the server, not what the app thinks it sent. This one has looked fine from the phone side for a long time.

Open Work reference: D2

M3The phone can only ever create one kind of categoryFix

When the user creates a category the type is hardcoded to WORK_TASK whatever they picked. The request succeeds, so the mistake is invisible until someone looks on the web and finds it in the wrong list.

Do

Send the type the user chose.

Finished when

Creating each kind of category from the phone puts it in the matching list on the web.

Open Work reference: D8

M4A category inside another category crashes the labels screenFix

The labels screen assumes every category sits at the top level. A category with a parent crashes it. It only works today because none of the categories in use have a parent — nothing prevents one being created.

Do

Handle a category that has a parent. If nesting is not something we support on the phone, skip nested categories rather than crashing — but say in the pull request which of the two you did.

Finished when

A category with a parent, created on the web, no longer crashes the phone.

Group 2 · Data the phone sends that quietly does not arrive

Each of these fails silently. Nothing on the phone shows a problem and nothing on the web shows the data.

M5Per-step timing is thrown away for the whole sessionHigh

The phone labels the recording type slightly differently from what the backend expects when it asks for a step’s time windows. Nothing matches, so no step events are recognised and the per-step timing of the entire session is lost — a work-cycle recording ends up with no per-task numbers at all.

Do

Send the recording type in the exact form the backend matches on. Check the backend’s own list of accepted values rather than guessing from the field name.

Finished when

A work-cycle recording produces per-task times on the web.

Open Work reference: D5

M6Lite mode corrupts a sensor’s details and loses its body partFix

A stray character in the sensor details sent from lite mode ends up inside one of the stored values. That sensor’s details are wrong and its body part is left out of the session, so the recording looks like it captured one limb fewer than it did.

Do

Find where the extra character is introduced and stop it there, rather than stripping it later.

Finished when

A lite-mode recording lists exactly the same body parts as the same recording in normal mode.

Open Work reference: D10

M7The phone still reads a field the backend deletedFix

A field the phone reads no longer exists in the backend’s answer, so everything that depended on it is quietly dead — no error, just behaviour that never happens.

Do

Find what that field was for. Either move it onto whatever replaced it, or remove the code that reads it along with everything it fed. Say which in the pull request.

Finished when

Nothing in the app reads a field the backend does not send.

Open Work reference: D9

Group 3 · The phone crashes on data it should tolerate

M8A work-cycle step with no time stops the operator from recording at allHigh

A step is allowed to have no duration — for example one imported from a spreadsheet with the time column blank. The phone requires a number, so the whole step list fails to load, and the operator cannot start the recording.

Do

Treat a missing duration as no duration, not as an error. The step still appears in the list and the operator can still work through it.

Finished when

A work cycle imported with a blank time column loads on the phone and can be recorded.

Open Work reference: D4

M9One bad record from the server leaves the screen stuck loadingHigh

A single malformed record crashes the whole work-cycle list instead of being skipped. The same happens on the company list and on email sign-in.

The shared safety net around repository calls only catches one of the two kinds of failure Dart has. A reply in an unexpected shape produces the other kind, so it goes straight past the net and the screen sits on its spinner forever.

Do

Widen the shared safety net so an unexpected reply is caught and turned into a normal failure the screen can show, instead of escaping.

On top of that, a list should survive one bad row: skip the row, show the rest, and report the bad one to Sentry.

Finished when

A deliberately malformed reply shows an error state on all three screens instead of an endless spinner.

Watch out

Fix the shared net first — it is one place and it covers every screen. The per-list tolerance is the second half.

Open Work reference: H11

Group 4 · Say what went wrong instead of pretending it worked

M10Picking an activity looks like it worked when it did notHigh

Choosing an activity closes the picker whether or not the choice was saved. The failure is reported to Sentry and the screen closes anyway, so the user goes back to the recording screen believing they picked something. The conditions screen behaves the same way.

Do

Keep the screen open when the save fails and show the problem there until it succeeds or the user backs out deliberately. Closing the screen must mean it saved.

Finished when

With the network off, picking an activity keeps the picker open and says it could not be saved.

Open Work reference: A7

M11Switching company while offline files the next recording under the old oneHigh

Switching company while offline reports success and never tells the server. The user believes they are in the new company; their next recording is filed under the old one.

Do

Either refuse the switch while offline and say why, or hold it and complete it when the connection comes back — and until it completes, do not show the user as being in the new company.

Pick whichever fits the offline model already in the app, and say which you picked.

Finished when

Switching company with no connection does not leave the app claiming to be in a company the server has never heard of.

Open Work reference: H9

M12Fields accept values the backend will refuseFix

Worker ID, workplace, comment, age, weight and resting heart rate all accept anything, so the user only finds out the value is wrong after submitting — and then usually only as a generic failure.

Do

Apply the backend’s own limits on the field, as the user types: length limits on the text fields, sensible ranges on age, weight and resting heart rate.

Take the limits from the backend’s model rather than inventing them. If a limit looks wrong, say so instead of choosing a different one.

Finished when

Every one of those six fields refuses, on the phone, a value the backend would have refused.

Open Work reference: E6

M13The “no organisation” message is hardcoded EnglishFix

In two places the app shows “Failed to create work session no Organization specified” whatever the app language. Everything else on that screen is translated.

Do

Move it into the translation files with the rest, in all five languages, and word it as something a user can act on rather than as a developer note.

Finished when

The message appears in the app’s language in all five languages.

Open Work reference: E12

Group 5 · Stop wasting the radio and the battery

M14Switching between the two kinds of Bluetooth scan leaves the first one runningFix

Starting the firmware scan cancels only the normal scan’s listener, and starting the normal scan cancels only the firmware one’s. The underlying scan keeps running either way, so the radio stays busy and devices found by the previous scan keep appearing in the new results.

Do

Stop the scan that is running — not just its listener — before starting the other one, and clear the results from the previous scan.

Finished when

Switching between the two scans twice in a row shows only devices from the scan currently running.

Open Work reference: F12

M15The sensor clock is re-synced before every single recordingFix

There is a shortcut meant to skip the re-sync when it was done recently. A units mistake means the condition can never be true, so it never fires and every recording starts slower than it needs to.

Do

Fix the units so the shortcut works, and say in the pull request what the skip window actually is once it does.

Finished when

Starting a second recording shortly after the first skips the clock sync, and the log shows it.

Open Work reference: F11

M16The recordings list piles up background work as you scrollFix

Each row in the list starts several background jobs and cleans up one of them. Scroll through a long list and the leftovers accumulate; a sync you started can keep running after you have left the screen.

Do

Every job a row starts must be cancelled when that row goes away, and everything the screen started must be cancelled when the screen closes.

Finished when

Scrolling a long recordings list and leaving it leaves no background work running.

Open Work reference: F10

Group 6 · Small, and only when the rest is done

M17The first heart-rate reading after a pause skews the recovery figureFix

That reading measures its gap from before the pause, so the gap is stretched across the whole break. The recovery figure comes out wrong for any session with a pause in it.

Do

Treat the reading after a pause as the start of a new stretch rather than a continuation of the one before the break.

Finished when

A session with a five-minute break shows a recovery figure in the same range as the same session without one.

Open Work reference: H10

M18The phone invents a first and last name out of the Worker IDFix

Worker records no longer have a first and last name. The phone still carries both fields and splits the Worker ID into a pretend first and last name to display it. Nothing is lost — it is just confusing to read, and the next person to touch this will assume those names mean something.

Do

Show the Worker ID as the Worker ID, and remove the two fields and the splitting along with them.

Finished when

No screen shows a first or last name for a worker, and neither field is sent any more.
