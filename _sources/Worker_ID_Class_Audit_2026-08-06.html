Silent-Failure Audit

Triggered by the duplicate Worker ID incident. This document contains the fix for that exact bug, and then every other place in the product where the same class of mistake is waiting to happen: a rule the user cannot see, enforced too late, reported in a way they cannot act on.

Each item is a ready-to-assign ticket — title and short description, no file paths, no prescribed solution. Under most of them is a shaded background note with the diagnosis and the exact location. That note is for you, not for the dev. If a diagnosis in it turns out to be wrong, the ticket above it is still correct.

What actually happened

Three separate faults lined up to produce one dead end.

The client typed Worker ID 1 and tapped Next. First, Worker ID is unique across the entire database rather than per company, so 1 was already taken — by another customer, whose data they cannot see. Second, the backend replied with a perfectly clear message, and the mobile app threw it away and showed the word “Bad request” instead. Third, nothing checked the ID while they were typing it, so they only found out after committing.

None of the three is hard to fix. What made it expensive is that all three are systemic — the same three patterns repeat across the product, and that is what the rest of this document is about.

Read this before assigning

Four issues here are worse than the one the client reported.

A1 lets one customer attach another customer's workers to their sessions. A2 is silently corrupting stored worker data on every single mobile session, today, for every customer. A4 means any worker invited from the web has never been able to record a session. These were not reported by anyone — they are quiet, which is exactly why they lasted.

Do first

A0 is the bug the client reported. A1 to A4 were found by this audit and are, in my judgement, more damaging.

A0Fix duplicate Worker ID producing a dead endBackendMobile

A user creating a worker types a Worker ID that already exists. Nothing warns them while typing, and when they continue they get an error saying only “Bad request”, with no way to understand or fix it. Four things need to change. One: Worker IDs must be unique per organization, not across the whole database — today a customer can be blocked by an ID belonging to a company they cannot see, and the error message confirms that company's record exists. Two: the mobile app must show the message the backend actually sent instead of its own generic text — this applies everywhere, not just this screen. Three: the Worker ID field must check availability as the user leaves it and show a red message under the field, blocking Next. Four: when the worker is only created at the end of a session, the ID must be validated at the start instead, so a finished recording can never be rejected.

Background — for Amine

Point one is a one-line model change plus a migration: worker_id is declared unique=True, and both create endpoints check Profile.objects.filter(worker_id=...) with no organization filter. It needs to become a unique-together on worker id + organization, and the two lookups need the org added.

Point three is smaller than it sounds — the backend already has this exact pattern for other fields: /users/email/check/ and /users/personal_number/check/ are availability endpoints the client panel already calls while the user types. Adding /users/worker_id/check/, scoped to the active org, and wiring it into both apps is the whole job.

Points two and four are covered in more depth by B2 and A3 — if you assign those, this ticket only needs points one and three.

A1Fix sessions being able to use another company's workersBackend

When a session is created, the backend looks up the worker and the ergonomist by their ID numbers and never checks that they belong to the company making the request. Anyone with a valid login can attach a worker or an ergonomist from a different customer to their own session, just by sending a different number. The lookups must be restricted to the organization the request belongs to, and return “not found” otherwise.

Background — for Amine

This is the same root mistake as the Worker ID bug, pointed the other way. The Worker ID rule was scoped too wide; here the lookup is not scoped at all. Both come from the same habit of fetching a record by primary key and trusting the number.

There are five unscoped lookups in the one function. The request already resolves the caller's organization a few lines above, so the fix is mechanical — but it needs a test, because nothing currently proves it. I have not checked whether this has ever actually been exploited; I am reporting that the code allows it.

user_sessions/views/session_views.py:216, 218, 230, 231, 249

A2Fix every mobile session overwriting the worker's gender and dominant armMobileBackend

Every time a session is started from the mobile app, the app sends the worker's gender and dominant arm in the wrong format, and the backend writes whatever it receives straight onto the worker's profile without checking it. The stored value ends up being something the system does not recognise as a valid gender or arm. This happens on every session, for every worker, and nobody is told. Fix the format the app sends, and make the backend reject values that are not one of the allowed options instead of saving them.

Background — for Amine

Concretely: the app sends female and Right; the system's allowed values are FEMALE and RIGHT. Django only enforces the allowed list on forms, not on direct assignment, and the helper that writes the profile assigns the raw string and saves. So the profile row now holds a value outside its own allowed set.

Two things make this worse than it looks. It runs on session start, every time — so it re-corrupts a worker every session, including workers whose details were entered correctly from the web. And the same helper also overwrites weight, age and resting heart rate from the session payload, so mobile silently wins over anything an admin edited in the client panel.

What I could not determine: whether gender or dominant arm feed into any ergonomic calculation. If they do, this has been quietly affecting results. Worth confirming with Farhad before deciding how far back it matters. I was not able to check the production database to measure how many rows are affected.

A3Fix a recorded session getting stranded when the worker cannot be createdMobile

When a user creates a new worker while offline, the app moves straight on without creating that worker. The worker is only created much later, at the end, when the session is synced. If the backend rejects it at that point — a duplicate ID, a value too long, anything — the recording is already done and there is no way to correct the worker details or try again. The only button is Close. Validate the worker as early as the connection allows, and when creation does fail at sync time, let the user edit the worker details and retry without losing the recording.

Background — for Amine

This is the mechanism that turned the client's small mistake into a real loss. Typing a duplicate ID is recoverable in two seconds if you are told immediately. Being told after a full recording session, with no edit and no retry, is what made it look broken.

The offline branch skips profile creation entirely and navigates forward; the summary screen then attempts the creation as the first step of sync. The recovery path is the important half of this ticket — even with A0 fixed, some other validation error will eventually land here.

A4Fix workers invited from the web never getting a worker profileWebBackend

Adding a worker from the Users page of the client panel creates their login and sends the invitation, but never creates their worker profile — the form does not even ask for a Worker ID, which is now required. When that worker logs into the mobile app and starts a session, the request fails with a server error. Either collect the Worker ID in that form and create the profile alongside the account, or stop offering the worker role there and point admins at the Workers page, which does it correctly.

Background — for Amine

This is fallout from the worker-naming refactor. The Workers page was updated to collect a Worker ID; the older “Add new user” flow on the Users page was not, and it is the one that can invite a worker with a login.

The failure at the other end is ugly: the session endpoint looks up the worker's profile, does not find one, and the exception is caught by a catch-all that returns a generic 500. So the worker sees a server error with no explanation — the same pattern as B1.

Worth asking the team which of the two paths is meant to be the real one. Having two different ways to add a worker, one of which is broken, is the actual problem.

B1Fix user mistakes being returned as “Something went wrong”Backend

Several endpoints wrap everything they do in a single catch-all that returns a generic server error. A duplicate value, a missing required field or an over-long name all come back looking identical to a genuine crash, so no client app can show anything useful. Separate the two: things the user can fix return a proper validation error with a specific message, and only real failures return a server error.

Background — for Amine

Affects session creation, session import, firmware create and update, and organization creation. Session import is the one that matters most — an import failing with no reason at all is a support call every time.

This also hides the real error rate from Sentry, because everything is logged as one generic exception.

B2Fix the mobile app hiding every error message the backend sendsMobile

The app reads the explanation the backend sends with an error, stores it, and then never shows it. Instead it displays its own fixed text — “Bad request”, “Not found”, “Internal server error” — regardless of what actually happened. Every clear message the backend produces is discarded before the user sees it. Show the backend's message when there is one, and fall back to the generic text only when there isn't.

Background — for Amine

This is the single change that would have prevented the client's incident from being a mystery. The backend was already returning “Worker ID "1" is already in use.” — the app had that string in memory and chose to print “Bad request”.

It is a small change in one file, and it improves every error screen in the app at once. If you only fund one ticket in this section, fund this one.

Why this keeps happening

Five habits produced every item in this document. Fixing the twenty-five tickets without changing these will produce a new list in three months.

1 · Rules are enforced at the last possible moment

The database is being used as the validator.

Length limits, allowed values and uniqueness are mostly enforced only when the row is written. By then the user is several steps past the field they got wrong, and the failure arrives as an exception rather than as advice. Every limit that exists on a database column should also exist on the form and in the serializer.

2 · Error messages are treated as noise

Both apps receive good explanations and print their own instead.

The backend often knows exactly what is wrong. The mobile app discards that text on every error. The client panel keeps only the general part and drops the per-field part. And some backend endpoints destroy the explanation before it is ever sent, by catching everything as one generic failure. One agreed error shape, one place that reads it, in each app.

3 · An ID number is trusted as proof of ownership

Records are fetched by number without asking whose they are.

Sessions, categories, labels and exports all fetch by ID and assume the caller is entitled to it. A helper that returns the caller's organization already exists and is used in some places and not others. Any lookup on a customer-owned table should go through it — and that is a review checklist item, not a one-off fix.

4 · The screen advances before the work is confirmed

Navigation happens first, the result is checked afterwards, if at all.

The worker form, the work library picker and the end of a recording all move the user forward before knowing whether the operation succeeded. When it fails, the user is somewhere else, and sometimes past the point where correcting it is possible. Nothing should navigate on the assumption of success.

5 · Nobody owns the shape of the data between the three apps

Two apps and a backend disagree about the same fields, quietly.

Gender arrives in a format the backend does not recognise and is stored anyway. Name fields are still sent to a place that deleted them. Two different screens create a worker and only one of them collects the required ID. None of this produces an error — it produces wrong data and broken accounts. This is the one that needs a decision from you rather than a ticket: what is the agreed shape, and who checks it.
