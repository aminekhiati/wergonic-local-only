A · Broken for users right now

A1A measurement you retry from Home never comes backHighWeb

The Home list shows measurements that need attention. When you retry a failed one, it disappears from the list immediately — and the app remembers that it is hidden, in your browser, forever.

So if the retry then fails again, the measurement never reappears on Home. You will not be told and you will not see it there again. It is also hidden only on your computer, so a colleague still sees it as if nothing happened, and if you sign in from a different machine it is back.

Do

An item should leave the Home list because the thing that put it there is resolved, not because someone clicked something. Work that out on the server, not in the browser.

A2A manual RAMP you saved cannot be opened againHighWeb

Create a RAMP by hand and you are taken straight into the form. You can fill part of it and press Save. But once you go back to the assessments list, that assessment cannot be opened — clicking the row does nothing.

Your answers are saved and unreachable, so the only way forward is to delete it and start over.

Do

An unfinished manual RAMP must reopen its form when you click it, the same way RULA and REBA already do.

Note for you

The code says this out loud — the comment above the click handler reads “pure-manual RAMP have no click-through”. It was written that way on purpose and never finished. Design it together with the save-and-resume feature at the back; it is the same screen.

A5Searching for a worker still misses part of an IDBackend

Half of this improved on its own. The Workers search now matches the start of any word in the ID, so typing 0451 finds SE2026-0451. What still fails is an ID with no separators: in SE20260451, only SE matches.

Do

Match anywhere in the ID. While you are there: age accepts any number at all, so ages like 333 are in the data. Limit it to something sensible.

A7Picking an activity on the phone looks like it worked when it did notHighMobile

Choosing an activity closes the picker whether or not the choice was saved. The failure is reported to Sentry and the screen closes anyway, so the user goes back to the recording screen believing they picked something. The conditions screen behaves the same way.

Do

Keep the screen open when the save fails and show the problem there until it succeeds or the user backs out deliberately. Closing the screen must mean it saved.

A11The admin panel throws away what you typedWeb

A failed save closes the organisation form and loses everything entered. Filters break on names containing “&” or spaces. The organisation filter silently drops selections the user did not touch. And the counts do not refresh after adding a user.

Note for you

Carried over from 10 August and not re-read since. No commit has touched those screens, so nothing can have changed — but nobody has opened them either.

A12A recording of zero seconds is treated as a real measurementWebBackend

A recording that captured nothing is marked complete, sits in the list like any other, and can be sent for a risk assessment. Nothing in the code looks at the duration before doing any of that.

Do

Mark it Failed instead, and do not offer it for assessment.

B · The numbers we report are wrong

Only what is not already written. Hand distance, the AI section, the 1.5 colour rule, the head column and the empty MEC questions are all fixed and waiting to be pushed — they are listed at the back.

B2The head’s own angle is never reported anywhereBackend

MEC questions 11.1 and 11.2 — the screen calls them “neck bending” — report the difference between the head and the trunk. The backend’s own internal name for them says they should be the head’s own angle.

The consequence either way is that the head’s own angle appears nowhere in MEC, so a worker whose head moves with their body always scores near zero on question 11.

Note for you

Waits on DEC-6. With 12.1 and 12.2 being deleted, the question is simply what 11 is supposed to measure. Nothing should be built until that is answered.

The two sensors record at different rates, so from the first dropped reading onwards it compares the head at one moment against the trunk at another, and the leftover readings are silently discarded. C · Security — nothing is broken, but the server trusts the app

Read before assigning

None of these affect a user, and none will show up in testing

Our apps always send the right values, so the product works. The gap is that signing in proves who someone is, not what they are allowed to touch — so someone calling the API directly, outside our apps, can send something ours never would. There is no sign any of it has been used. Whether to fund it now is DEC-3.

C1The server decides whose data to return from the request, not from who is signed inHighBackend

Several Work Library endpoints — activities, conditions, and the labels put on a recording — pick which company’s data to use from a number in the web address rather than from the signed-in user. Any valid login can read, create, edit or delete another company’s data by sending a different number.

Do

Take the company from the signed-in user and ignore the one in the address.

Note for you

Six endpoints still work this way; four in the same area were already corrected, so there is a pattern to copy. This is not dead legacy code — those rows are today’s activities and conditions, and both apps use them.

IDWhereTask
C2BackendA recording’s activity or condition can be re-pointed at another company’s. Attaching one is checked; changing it afterwards is not. Apply the same check on edit.
C3BackendThe default for the whole API is still “anyone may call this”, so any endpoint where a developer forgets to say otherwise is public. Make the default “must be signed in” and mark the genuinely public ones — sign-in, register, password reset.
C4BackendThe backend answers to any address, and the full list of its endpoints is readable without signing in. Restrict both outside development.
C5BackendThe statistics export answers differently for a recording that belongs to another company than for one that does not exist, which lets an outsider work out which recording numbers are real. Answer the same way in both cases.

D · The phone and the backend disagree

Things the app sends that the backend does not accept. Each one fails quietly. D1, D2, D7 and D8 are the same code — do them as one job.

D1The phone still calls the old address for labels, categories and eventsHighMobile

The backend moved activities and conditions to the Work Library and the web app followed. The phone still calls the old /categories/… address for all four of its calls: fetching a category with its labels, creating a category, creating a label, and uploading the session’s events.

This works today only because the old endpoints have not been switched off. The day they are, every activity and label action on the phone stops, and no session events upload at all.

Do

Move all four calls onto the Work Library API, the one the web app uses. Statuses and the activity lists are already on the new API, so this is a finishing job rather than a rewrite — follow what is there.

Do this before D2, D7 and D8. They touch the same code, and doing them separately means touching it three more times.

D2Break markers never save, and they take the rest of the session with themHighMobile

A break is recorded against label number 0. That label does not exist on the backend, so the upload is refused. Because all of a session’s events go up in a single request, one break means none of that session’s events are saved — not the activities, not the tasks, nothing.

Do

A break is a real thing that happened during the recording and it must reach the server. Send it as something the backend accepts rather than as a label that does not exist.

Whatever the shape, one event failing must never stop the others: send them so a single bad event is rejected on its own and the rest still land.

Note for you

Check what actually reaches the server, not what the app thinks it sent. This has looked fine from the phone side for a long time.

IDWhereTask

The phone requires a number, so the whole step list fails to load and the operator cannot start recording at all. Treat a missing duration as no duration, not as an error.
D5MobilePer-step timing is thrown away for the whole session. D8MobileThe phone can only ever create one kind of category — the type is hardcoded whatever the user picked — and the request succeeds, so the mistake is invisible until someone looks on the web and finds it in the wrong list.
D9MobileThe phone still reads a field the backend deleted, so anything that depended on it is quietly dead. Either move it onto whatever replaced it or remove the code that reads it along with everything it fed — and say which.
D10MobileA stray character in the sensor details sent from lite mode ends up inside one of the stored values, so that sensor’s details are wrong and its body part is left out of the session. A lite-mode recording should list the same body parts as the same recording in normal mode.

Features, not bugs

Feature

An assessment you can save and come back to

A RULA, REBA or RAMP form is all-or-nothing today: fill in half of it, click away, and everything since the last Save is gone with no warning. There is no autosave and no draft.

The answer is a proper unfinished state the user controls — save what you have, see it marked as unfinished in the list, open it later and carry on. Design it together with A2, which is the same screen.

Feature

Choose how many rows you see

No list in the product lets you change the number of rows per page. Measurements is fixed at ten. If you want a control for it, it is new work — the old one is gone with the screens it lived on.
