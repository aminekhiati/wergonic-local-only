Mobile App — Improvement Tasks

The brief for the next round of work on the Wergonic mobile app. It defines what to change and why. Exact layout, placement and visual treatment are the designer's call — any specific arrangement described here is illustrative, not prescriptive. All renames are UI-only: database fields, API payloads and model classes do not change.

5 phases · audited against the dev branch · updated 29 June 2026

Setup flow — step order

The redesigned setup wizard runs in this order. Conditions sit right after the worker, before any hardware step.

Home → Worker → Conditions → Work Setup → Pairing → Calibration → Measurement
Backend dependencies — not mobile work

What the app needs from the backend before Phase 2

The mobile dev does not build these. They must exist before the Conditions step and the activity picker can be built. The data already exists in the web prototype — this is about exposing it and agreeing the contract. Do not invent payload shapes; confirm them with the backend.

  • Activities endpoint — the org's activity groups and their activities (the closed list the user picks from during recording).
  • Conditions endpoint — the org's condition groups, each with its selection type (single-choice / multi-choice) and its values.
  • Sync payload — extend the measurement sync to carry the selected condition values, so they are stored server-side.

Phase 2 · Setup Flow Redesign

2.1 Home Screen

Today the home is a launcher only — a single "New measurement" button and a small unsynced banner. Most opens are repeat setups, so the home should make repeating and resuming fast.

  • Quick Start — surface the last setup so it can be repeated in one tap (reconnect → recalibrate → record). Work Cycle: "Record [Worker] at [Station]?". Free: "Record [Worker]?".
  • Sync status — when measurements are waiting to sync, show how many and a way to sync. Hide when there's nothing pending.
  • Recent measurements — the last few as compact cards (worker, date, duration, sync status); tap to open or sync.
  • Sensor status — battery and connection for cached sensors, so a dead sensor is never a surprise.

2.2 Worker Selection

Today it's a paginated search field only. Ergonomists reuse the same 5–10 workers.

  • Recent workers — surface recently-used workers (from the local cache described below) for one-tap selection, with live search for anyone else and a clear "New Worker" action.
Offline gap — cache workers on use, not the whole org. Today the worker list is fetched live from the API; selecting a worker keeps it in memory only and never stores it, and the local store holds just the account's own profiles — so offline there's nothing to pick from and the app forces new-worker creation. Fix: when a worker is selected online, persist that profile locally (the save path already exists). The step then reads recent/cached workers from local storage — instant, and works offline. Online search stays for discovering workers not yet cached; "New Worker" (already offline-capable) covers the rest. No org-wide sync, no bulk download.

2.3 Conditions Step new

Conditions are whole-measurement metadata (e.g. Shift Type, Environment), defined per org in the Work Library. Today the app has no support for them — they can only be added after the measurement, from history, which means they get skipped.

  • Add a dedicated step after worker selection, before the hardware steps (see flow above). Asking upfront matters — conditions (shift, weather) are known at the start; asking at the end gets skipped.
  • Render each condition group as a selector driven by its type: single-choice → pick one; multi-choice → pick several. (Visual treatment is the designer's call.)
  • If the org has no conditions configured, skip this step automatically.

2.4 Work Setup Step

Today the user is forced to choose between "Work Task" and "Work Cycle" regardless of what the org actually has. The step should adapt to the org's configuration instead of making the user reason about terminology.

  • Org has only Work Cycles → go straight to the hierarchy picker (Factory → Line → Station → Operator → Model); surface recently used cycles.
  • Org has only Activities → no choice to make; it's a Free Measurement. Continue straight through — do not ask the user to pre-declare activities.
  • Org has both → offer a clear choice: Work Cycle or Free Measurement.
Two decisions applied here. (1) The old "ask the user which activities they expect to record" idea is removed — it was vague and made both the user and the dev guess. In a Free Measurement, activities are chosen live during recording via an easy, searchable picker (see 3.3). (2) Naming: kept as "Free Measurement", paired with "Work Cycle" — deliberately reusing the one noun "measurement" rather than introducing "session" or "recording" as competing words for the same thing.

2.5 Pairing

  • If sensors are cached from the last measurement, auto-reconnect and make it visible that this is happening (today the cache reconnect is silent).
  • Per-sensor, limb-specific status: "Reconnecting Left Arm…" rather than a generic "Connecting…".
  • Show battery level per sensor during pairing — the app already tracks real % (BatteryTracker / BatteryLabel), so make sure the pairing cards use it rather than only an OK/low icon.
  • If all sensors reconnect successfully, auto-advance to calibration.

2.6 Calibration

The current flow with videos works well — only small additions.

  • After the last calibration succeeds, auto-advance into the measurement — one less tap.

Phase 3 · Measurement Screen Overhaul

3.1 Top Bar: Current Activity + Time

  • Show what's being recorded and elapsed time. Work Cycle: "Task 3/7: Quality Check · 02:15". Free: "Lifting · 12:34".

3.2 Work Cycle: Task Timeline

The auto/manual toggle works well. These additions give more context and control.

  • A progress bar showing all tasks as proportional segments (completed / current / upcoming).
  • Auto mode — countdown for the current task ("Next in 0:45") with an "Extend 30s" option near zero, and a brief "Now: [Next Task]" cue on advance.
  • Manual mode — show elapsed vs expected ("2:15 / 3:00") and make "Next Task" prominent.

3.3 Free Measurement: Activity Switching

Reworked to match 2.4 — there is no pre-selected activity list anymore; everything is chosen live.

  • Show the current activity on the measurement screen.
  • A searchable activity picker to switch: surface recently/last-used activities for one-tap, with search-as-you-type over the full list. Switching must be fast and low-friction mid-measurement.
  • Starting a new activity automatically ends the previous one — no extra tap.

3.4 Break Behavior

  • Adding a break auto-pauses; ending it auto-resumes. (Today a break already pauses data writing — keep that, just make the pause/resume explicit and obvious.)
  • Breaks appear as distinct segments in the task timeline.
  • Decide intended behavior for advancing tasks while paused — today "Next Task" is blocked during a break, which may or may not be wanted.

3.5 Fix the in-session settings menu bug

The gear icon shown during a measurement opens a menu with two items, and both are problematic — this is the issue spotted in review.

  • "Settings" is permanently disabled (hardcoded, no handler) — dead UI. Either wire it to the settings it implies, or remove it.
  • "Limbs Recalibration" works only before Start (armed state) and is disabled once recording begins. Decide: if a sensor drifts mid-measurement there's currently no recovery. Either allow recalibration mid-session (likely via a pause) or, at minimum, don't present a control that never works in that state.
  • Principle: a measurement should never show controls that are disabled in every state the user can actually reach.

3.6 Make feedback warm-up visible bug

  • Live limb feedback (colours + voice) does not start until the "accumulated feedback first delay" elapses — default ~10 minutes. On short measurements the user may never see feedback and is never told why.
  • Surface the warm-up (e.g. indicate feedback is pending / when it starts) and reconsider whether the default delay should be that long.

Phase 4 · Completion & Measurements List

4.1 Completion Screen

Today the summary after a measurement is minimal — no confirmation that metadata was captured.

  • Show a completion checklist: worker, duration, limbs recorded, activities, conditions.
  • If conditions were not set during setup, prompt to add them here.
  • Make syncing the primary action, with "Save & sync later" as the secondary.

4.2 Measurements List

  • Filters above the list: All / Synced / Pending / Today / This Week.
  • Richer cards: worker, date, duration, activity count, sync status.
  • A proper empty state with a CTA.
  • Swipe to delete.

Phase 5 · Settings, Onboarding & Work Library

5.1 Settings Restructure

Today settings are one long scroll with technical labels.

  • Group into clear sections: Sensors & Hardware, Feedback During Recording, Measurement Defaults, Organization, Work Library (read-only), App.
  • Add a short description under each section header.
  • Developer settings are already hidden behind a 7-tap gesture — so this is mostly about grouping and plain-language labels, not hiding.
  • Disambiguate the two feedback settings so they aren't confused: "Feedback interval" (voice, seconds) vs the developer "Instant feedback refresh rate" (Hz).

5.2 Work Library (Read-Only) new

No in-app view of the org library exists today.

  • A read-only view of the org's Work Library: Activities (groups + activities), Conditions (groups + values), Work Cycles (the hierarchy). Editing stays on the web.

5.3 Onboarding new

There is no first-time onboarding today — users land straight on the home screen.

  • A short 3-screen intro for first-time users, ending in "Let's start your first measurement" → straight into the setup wizard.

Do Not Change

  • BLE / sensor layer — just stabilized after the native Kotlin migration.
  • Sync mechanism — works; don't refactor.
  • Calibration logic and videos — working well; only add UI around them.
  • Database fields / API payloads — all renames are UI-only; backend migration is separate.
  • Dark theme — keep it; suits industrial environments.
  • "Work Task" inside Work Cycles — stays as is.
